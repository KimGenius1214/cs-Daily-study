🧭 사이드바 내비게이션 내비게이션·탭

관리자 화면·정산 콘솔처럼 메뉴가 20개를 넘어가면, 사이드바는 "다 펼쳐 보여주기"와 "좁게 접기" 사이에서 타협해야 합니다. 요즘 기준은 레일(rail) 축소 모드 + 중첩 그룹 접기 + 현재 위치 명시 세 가지입니다.

한 줄 용어

  • 레일(rail) — 사이드바를 아이콘 폭(대략 56~64px)만 남기고 접은 상태. 메뉴를 완전히 숨기지 않고 "위치 감각"을 유지합니다.
  • aria-current="page" — "지금 보고 있는 페이지가 이 링크"라고 보조기기에 알리는 속성. 색만 칠하면 스크린리더는 알 수 없습니다.
  • aria-expanded — 접힘/펼침 버튼이 지금 열려 있는지를 알리는 속성. 값은 "true"/"false" 문자열입니다.
  • 스킵 링크(skip link) — 키보드 사용자가 긴 메뉴를 전부 Tab 하지 않고 본문으로 건너뛰게 해주는 첫 링크.

결제 내역

메뉴를 클릭하면 aria-current="page"가 그 링크로 옮겨 갑니다. 색 표시(왼쪽 세로 막대)와 속성이 항상 같이 움직이는지가 핵심입니다.

현재 위치: 결제 내역

① 그룹 헤더(결제/정산/설정)는 <button aria-expanded>. ② 레일 모드에선 라벨을 감추는 대신 ::after 툴팁을 hover와 :focus-visible 둘 다에 붙여 키보드 사용자도 이름을 볼 수 있게 했습니다. ③ 배지(7)는 레일에서도 사라지지 않고 아이콘 우상단으로 이동합니다 — "접었더니 알림이 안 보인다"가 가장 흔한 사고입니다.

언제 무엇을 쓰나

상황선택이유
메뉴 8개 이하, 데스크톱 위주고정 사이드바(항상 펼침)접는 기능 자체가 불필요한 복잡도
메뉴 15~40개, 표·차트가 넓게 필요레일 축소 + 그룹 접기가로 공간을 되찾으면서 위치 감각 유지
모바일 폭(≈560px 미만)드로어 또는 하단 탭바레일도 화면의 15%를 먹음. 이미 다룸: 바텀 네비게이션
메뉴 깊이 3단 이상2단으로 접거나 검색·⌘K 병행3단 트리는 클릭 수가 급증. 이미 다룸: 커맨드 팔레트

💻 복붙용 핵심

<!-- 그룹: 버튼 + aria-expanded, 목록은 인접 형제 -->
<button class="grouphead" aria-expanded="true" aria-controls="g1">결제</button>
<ul class="navlist" id="g1">
  <li><a href="/payments" data-label="결제 내역" aria-current="page">
    <span class="ico" aria-hidden="true">💳</span><span class="lbl">결제 내역</span>
  </a></li>
</ul>

/* JS 없이 접기: 닫힌 버튼의 "다음 형제"를 숨긴다 */
.grouphead[aria-expanded="false"] + .navlist { display: none; }

/* 레일 모드 툴팁 — hover만 걸면 키보드 사용자는 이름을 못 본다 */
.app.rail .navlist a::after { content: attr(data-label); opacity: 0; /* ...위치... */ }
.app.rail .navlist a:hover::after,
.app.rail .navlist a:focus-visible::after { opacity: 1; }

♿ 접근성·상태 설계

  • 현재 위치는 색이 아니라 속성으로. aria-current="page"가 진실이고, 배경색·세로 막대는 그 시각적 표현일 뿐입니다. 둘이 어긋나면 스크린리더 사용자는 길을 잃습니다.
  • 레일에서 라벨을 display:none으로 지우면 스크린리더도 못 읽습니다. 이 데모는 data-label을 툴팁으로 다시 노출하지만, 실무에선 aria-label을 <a>에 직접 달아 두는 편이 안전합니다.
  • 스킵 링크를 메뉴 맨 앞에 두세요. 메뉴 항목이 12개면 본문에 닿기까지 Tab 12번입니다. (데모에서 사이드바 안을 Tab으로 진입해 보면 첫 포커스가 스킵 링크입니다.)
  • 포커스 링을 안쪽으로. 좁은 레일에선 outline-offset:2px가 잘려 보입니다. 여기선 outline-offset:-1px로 안쪽에 그렸습니다.
  • 접힘 상태는 사용자 선택으로 기억. 실무에선 localStorage에 저장합니다(이 데모는 새로고침하면 초기화).
흔한 사고 — 그룹을 <div onclick>으로 만들면 키보드로 열 수 없고 스크린리더가 "버튼"이라고 읽지도 않습니다. 접히는 헤더는 반드시 <button type="button">입니다. (type을 빼면 폼 안에서 submit이 됩니다.)

🃏 클릭 가능한 카드 카드·리스트

"카드 아무 데나 눌러도 상세로 가게 해주세요"는 기획에서 매번 나오는 요구입니다. 그런데 카드 안에는 보통 버튼(정산 상세, 영수증)이 같이 들어 있고, 사용자는 카드 안 글자를 드래그해 복사하기도 합니다. 이 셋을 동시에 만족시키는 방법은 사실상 하나로 굳어졌습니다.

한 줄 용어

  • 블록 링크(block link) — 카드·행 전체를 하나의 링크로 만드는 패턴.
  • 가상 요소(pseudo-element) — ::before/::after로 HTML에 없는 빈 상자를 만들어 내는 CSS 기능. 여기선 "투명한 클릭 판"으로 씁니다.
  • 접근 가능한 이름(accessible name) — 스크린리더가 링크를 읽을 때 부르는 이름. 링크 안 텍스트를 전부 이어 붙여 만들어집니다.

💻 복붙용 핵심

<article class="mcard">
  <h5><a href="/payments/9021">쿠팡</a></h5>   <!-- 링크는 "이름"에만 -->
  <p class="amt">₩ 132,000</p>
  <p class="sel">승인번호 30284471</p>
  <div class="acts"><button>영수증</button></div>
</article>

.mcard { position: relative; }

/* 투명한 클릭 판을 카드 전체에 깐다 */
.mcard h5 a::after { content: ""; position: absolute; inset: 0; z-index: 1; }

/* 판 위로 띄워야 따로 눌리는 것들 */
.mcard .acts,
.mcard .sel { position: relative; z-index: 2; }

/* 포커스 링은 링크가 아니라 카드에 그린다 */
.mcard h5 a:focus-visible { outline: none; }
.mcard:has(h5 a:focus-visible) { outline: 3px solid var(--ring); outline-offset: 2px; }

:has()는 "안에 ○○를 가진 요소"를 고르는 CSS 선택자입니다. 여기선 "포커스된 링크를 품은 카드"를 골라 링을 카드 테두리에 그립니다.

♿ 접근성·상태 설계

  • 링크 이름은 짧게. 스크린리더에는 "링크 목록"만 뽑아 훑는 기능이 있습니다. 카드 전체를 감싸면 그 목록이 문단으로 가득 찹니다.
  • 텍스트 선택 문제. 오버레이 판 위에서 드래그하면 글자가 잡히지 않습니다. 복사할 값(승인번호, 주문번호)만 z-index:2로 올려 주세요. 판 전체를 드래그 가능하게 만들려면 mousedown~mouseup 이동 거리가 임계값(예: 6px)을 넘으면 이동을 취소하는 JS가 필요합니다.
  • 커서·호버는 카드에. 링크에만 :hover를 걸면 카드 빈 곳에 올렸을 때 아무 반응이 없어, 눌러도 되는지 알 수 없습니다.
  • 안쪽 버튼 주변에 여백. 판이 버튼 바로 옆까지 살아 있으면 모바일에서 손가락이 1~2px 빗나갈 때 상세로 튕겨 나갑니다.
  • 터치에서의 :hover 잔상은 @media (hover: hover)로 감싸 두면 줄어듭니다.
Next.js에서 — <Link>가 <a>를 그대로 뱉으므로 위 CSS를 그대로 씁니다. 단 카드 안 버튼의 onClick에는 e.stopPropagation()이 아니라 레이어 분리(z-index)로 푸는 게 맞습니다. 버튼이 판 위에 있으면 애초에 링크로 이벤트가 가지 않습니다.

🌀 스크롤 연동 애니메이션 트렌드·개념

"스크롤하면 진행률 바가 차오르고, 카드가 아래에서 떠오른다"를 예전엔 IntersectionObserver나 GSAP·Framer Motion으로 만들었습니다. 이제는 CSS 두 줄 — animation-timeline: scroll()과 view() — 로 같은 걸 하고, 그 계산이 메인 스레드 밖에서 돕니다.

한 줄 용어

  • 타임라인(timeline) — 애니메이션의 "진행도 0%→100%"를 무엇으로 잴지. 기본값은 시간이고, 여기선 스크롤 위치로 바꿉니다.
  • scroll() — 스크롤 컨테이너의 스크롤바 위치가 0%→100%. 진행률 바에 씁니다.
  • view() — 그 요소가 화면(스크롤 영역)을 지나가는 동안이 0%→100%. 요소별 등장 효과에 씁니다.
  • animation-range — view()의 몇 %~몇 % 구간만 쓸지 자르는 속성. entry(들어오는 중) / cover(걸쳐 있는 전체) / exit(나가는 중).
  • 메인 스레드 — JS가 도는 하나뿐인 줄. 여기서 스크롤마다 계산하면 스크롤이 끊깁니다.

① scroll() — 진행률 바 + ② view() — 카드 등장

현재: 애니메이션 켜짐

실제로는 OS 설정(Windows: 설정 › 접근성 › 시각 효과 › 애니메이션 효과)이 prefers-reduced-motion을 켭니다. 이 버튼은 그 상황을 흉내 내 애니메이션을 끄되 콘텐츠는 그대로 보이게 하는 처리를 보여줍니다.

💻 복붙용 핵심

/* ① 진행률 바 — 스크롤 컨테이너에 "이름"을 붙여 묶는다 */
.scroller {
  overflow-y: auto;
  scroll-timeline-name: --report;   /* 이 스크롤에 --report라는 이름을 준다 */
  scroll-timeline-axis: block;      /* 세로 스크롤 기준 */
}
.progbar > i {
  transform: scaleX(0);              /* 미지원 브라우저의 기본값 */
}
@supports (animation-timeline: scroll()) {
  .progbar > i {
    animation: growX linear both;
    animation-timeline: --report;    /* 조상 중 그 이름을 찾아 붙는다 */
  }
}
@keyframes growX { from { transform: scaleX(0) } to { transform: scaleX(1) } }

/* ② 요소 등장 — "내가 지나가는 동안"이 0%→100% */
@supports (animation-timeline: view()) {
  .rvcard {
    animation: rise linear both;
    animation-timeline: view();
    animation-range: entry 5% cover 32%;  /* 들어오기 시작~조금 걸친 지점까지 */
  }
}
@keyframes rise {
  from { opacity: 0; transform: translateY(22px) scale(.97) }
  to   { opacity: 1; transform: none }
}

/* ③ 모션 줄이기는 선택이 아니라 필수 */
@media (prefers-reduced-motion: reduce) {
  .rvcard { animation: none !important; opacity: 1 !important; transform: none !important }
}
오늘 만들다 실제로 밟은 함정 — 진행률 바를 처음엔 animation-timeline: scroll(nearest)로 짰는데 전혀 움직이지 않았습니다. 바가 position: sticky인 헤더 안에 들어 있었기 때문입니다 (같은 스크롤 박스 안이라도 nearest 해석이 sticky 조상에서 어긋나는 것으로 보입니다 — 이 동작이 명세대로인지 Chrome 특성인지는 확인하지 못했으니 추정). 해결은 이름 있는 타임라인입니다: 스크롤 컨테이너에 scroll-timeline-name: --report를 붙이고 애니메이션 쪽에서 animation-timeline: --report로 지목하면 확실합니다.
👉 실무 규칙으로 삼을 만한 것: scroll()·view()가 조용히 안 먹으면 먼저 이름 있는 타임라인으로 바꿔 본다. 타임라인이 해결되지 않으면 에러도 경고도 없이 그냥 0% 상태로 멈춰 있습니다. (디버깅 팁: el.getAnimations()[0].effect.getComputedTiming().progress가 null이면 타임라인이 안 붙은 것입니다.)
브라우저 지원 — Chrome/Edge 115+, Firefox 132+, Safari 18+ 에서 animation-timeline·scroll()·view()가 동작합니다. 2026년 중반 기준 전 세계 지원율은 대략 84% 수준으로 보고됩니다(수치는 출처에 따라 다를 수 있어 추정치로 봐 주세요). 구형 브라우저에선 @supports 밖의 기본 스타일이 그대로 보이도록 짜는 게 안전합니다.

🧠 어디에 쓰고, 어디엔 쓰지 말까

쓸 만한 곳쓰지 말아야 할 곳
긴 약관·정산 리포트의 읽기 진행률 바 결제 확인 화면 — 금액·버튼이 애니메이션으로 늦게 나타나면 오조작·불신을 부릅니다
랜딩/온보딩에서 섹션이 떠오르는 연출 에러·경고 메시지 — 즉시 100% 보여야 합니다
가로 캐러셀의 "현재 항목" 강조 스크롤할 때마다 레이아웃이 바뀌는 효과(글자 크기·높이) — 읽던 위치가 튑니다
스크롤에 반응해 축소되는 헤더 목록 항목 수백 개에 전부 view() — 스크롤 자체는 안 끊기지만 시선이 피로해집니다
왜 굳이 CSS로 옮기나 — IntersectionObserver는 "보이기 시작함/끝남"이라는 불연속 신호만 줍니다. 스크롤 양에 비례하는 효과(진행률, 되감기)를 만들려면 결국 스크롤 이벤트를 직접 듣게 되고, 그 계산은 메인 스레드에서 돕니다. animation-timeline은 이 관계를 브라우저에 선언으로 넘기므로 스크롤이 빨라도 값이 밀리지 않습니다. 다만 정확한 성능 이득은 기기·페이지마다 다르므로 실제 프로젝트에선 측정해 보는 게 맞습니다.
