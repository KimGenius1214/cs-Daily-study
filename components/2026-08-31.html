🔘 제출 버튼의 "처리 중" 상태 버튼·액션

결제 버튼을 두 번 눌러 두 번 결제되는 사고는 대부분 UI에서 시작됩니다. 잠금(락) · 라벨 유지 · 실패 복귀 · 성공 후 재잠금, 네 가지를 실제로 눌러 보며 비교합니다.

변형 1 — 잠금 없는 버튼 vs 잠금 + 멱등키 버튼

잠금을 끄고 결제 버튼을 빠르게 3~4번 눌러 보세요. 요청이 그대로 여러 번 나갑니다. 잠금을 켜면 첫 클릭 이후 눌러도 요청이 늘지 않습니다.

서버가 받은 결제 요청

아직 요청 없음

    멱등키(idempotency key) = "같은 요청을 두 번 보내도 한 번만 처리해 달라"고 서버에 알려 주는 1회용 식별자입니다. UI 잠금은 뚫릴 수 있으니(느린 네트워크, 뒤로가기, 새로고침) 키를 함께 보내 서버에서 최종 방어합니다.

    변형 2 — 처리 중 · 실패 복귀 · 성공 후 잠금

    처리 중에는 라벨을 지우지 않고 스피너만 앞에 붙이고, 버튼 최소 너비를 고정해 화면이 튀지 않게 합니다. 실패하면 원래 상태로 돌아가 다시 누를 수 있어야 하고, 성공하면 다시 활성화하지 않습니다(결제는 재클릭 자체가 사고).

    상태버튼이 해야 할 일흔한 실수
    idle금액·행동을 라벨에 명시("54,000원 결제하기")"확인" 같은 무의미한 라벨
    pendingdisabled + aria-busy="true", 라벨 유지, 너비 고정라벨을 "..."로 바꿔 버튼 폭이 줄어듦
    error버튼 원복 + 버튼 근처 인라인 에러 + role="alert"토스트만 띄우고 버튼은 계속 잠김
    success완료 표시 후 잠금 유지, 다음 화면으로 이동성공 후 버튼을 다시 활성화 → 이중 결제
    왜 disabled만으로 부족한가. disabled 버튼은 포커스를 잃고 스크린리더가 읽지 않아, 키보드 사용자는 "내가 누른 게 처리되고 있는지" 알 수 없습니다. 그래서 별도의 role="status" 영역에 "결제를 처리하고 있습니다"를 함께 알리거나, aria-disabled="true" + 클릭 무시 방식으로 포커스를 유지하는 절충안을 씁니다.

    💻 코드

    // 제출 잠금 + 멱등키 (프레임워크 무관 최소 형태)
let inFlight = false;
let idemKey = null;

async function pay(){
  if (inFlight) return;                 // 1) UI 잠금
  inFlight = true;
  idemKey ??= crypto.randomUUID();      // 2) 재시도해도 같은 키를 유지
  setState('pending');
  try {
    await api.pay({ amount: 54000 }, { 'Idempotency-Key': idemKey });
    setState('done');                   // 3) 성공하면 다시 열지 않는다
  } catch (e) {
    inFlight = false;                   // 4) 실패만 복귀 — 키는 그대로 재사용
    setState('error', e.message);
  }
}

    ⌨️ 기간 선택 필터 입력·폼

    정산·거래내역 화면의 기본 입력은 "기간"입니다. 캘린더 라이브러리를 붙이기 전에, 네이티브 <input type="date"> 두 개 + 프리셋 칩 + 상호 제약만으로 실무 요구의 대부분이 해결됩니다.

    — 0일

    막대는 조회 한도(92일) 대비 선택한 기간의 비율입니다.

    🧩 여기 들어간 규칙 5가지

    • 프리셋 먼저. 실무에서 90%는 "최근 7일 / 이번 달"입니다. 캘린더를 열기 전에 한 번의 클릭으로 끝내게 합니다. 선택된 칩은 aria-pressed="true"로 표시합니다.
    • 상호 제약. 시작일을 고르면 종료일 입력의 min이 그 날짜로, 종료일을 고르면 시작일의 max가 그 날짜로 바뀝니다. 브라우저가 잘못된 조합을 애초에 못 고르게 막습니다.
    • 미래 차단. 두 입력 모두 max를 오늘로 둡니다. 정산 데이터는 미래에 없습니다.
    • 한도 초과는 막지 말고 고쳐 주기. 92일을 넘기면 에러만 띄우는 대신 "최근 92일로 맞추기" 버튼을 함께 줍니다. 사용자가 다시 계산하지 않게 합니다.
    • 같은 기간 앞뒤 이동. ← → 버튼이 선택된 길이(예: 7일)를 유지한 채 통째로 옮깁니다. "지난주랑 비교"가 클릭 한 번이 됩니다.
    네이티브 date 입력의 한계도 알아 두기. 표시 형식(2026/08/31 vs 08/31/2026)은 브라우저·OS 로캘이 정하며 CSS로 바꿀 수 없고, 캘린더 팝업 모양도 커스터마이즈가 거의 안 됩니다. 값은 항상 YYYY-MM-DD 문자열이라 서버 연동은 오히려 단순합니다. 브랜드 캘린더가 꼭 필요할 때만 라이브러리로 올라가면 됩니다. (다크 모드 대응은 color-scheme으로 — 이 데모도 그렇게 했습니다.)

    ♿ 접근성 체크

    • 프리셋은 <button> + aria-pressed — 스크린리더가 "눌림" 상태를 읽습니다. div에 클릭 핸들러를 붙이면 키보드로 못 씁니다.
    • 화살표 버튼은 아이콘만 있으므로 aria-label 필수("이전 기간으로 이동").
    • 한도 초과 메시지는 role="alert"로 즉시 읽히고, 문제 입력에는 aria-invalid="true"를 겁니다.
    • 일수 배지는 색(초록/빨강)만으로 구분하지 않고 숫자 텍스트를 함께 둡니다.

    🌀 Invoker Commands — 버튼이 JS 없이 다이얼로그를 여는 표준 트렌드·개념

    <button command="show-modal" commandfor="dlg">. 이 두 속성만으로 버튼이 다이얼로그·팝오버를 열고 닫습니다. Invoker(인보커) = "다른 요소를 작동시키는 버튼"이라는 뜻입니다.

    지원 여부 확인 중…

    변형 1 — 내장 커맨드 (JS 0줄)

    이 두 버튼에는 클릭 핸들러가 하나도 없습니다. 브라우저가 열기·최상단 레이어 배치·포커스 이동·Esc 닫기·닫힌 뒤 원래 버튼으로 포커스 복귀까지 처리합니다. (미지원 브라우저에서는 아래 폴백 스크립트가 대신 동작합니다.)

    환불을 진행할까요?

    54,000원이 원결제 수단으로 환불됩니다. 이 동작은 되돌릴 수 없습니다.

    팝오버입니다

    바깥을 클릭하거나 Esc를 누르면 닫힙니다 — 이것도 브라우저 기본 동작입니다.

    변형 2 — 커스텀 커맨드 (--로 시작)

    pay_9f31c0a8 복사했습니다
    커스텀 커맨드는 이름이 --로 시작해야 합니다. 대상 요소에서 command 이벤트를 받아 e.command로 분기하면, 어떤 버튼이 눌렸는지 일일이 addEventListener를 붙이지 않아도 됩니다.

    동작 로직이 버튼이 아니라 "대상 요소"에 모입니다. 목록에 버튼이 100개 있어도 리스너는 대상 쪽 하나면 됩니다.

    📈 왜 지금 뜨나

    • 2025년 하반기 Safari 지원이 붙으면서 주요 엔진(Chrome·Edge·Firefox·Safari)이 모두 지원하게 되어 Baseline(주요 브라우저 공통 사용 가능 기준)에 들어왔다고 알려져 있습니다. 실제 프로젝트 도입 전에는 caniuse·MDN에서 현재 수치를 다시 확인하시길 권합니다.
    • 지금까지 모달 하나를 제대로 만들려면 포커스 트랩(모달 안에 Tab 가두기), Esc 닫기, 스크롤 잠금, 닫은 뒤 포커스 복귀를 직접 짜야 했습니다. dialog + Invoker 조합은 이걸 브라우저가 맡습니다.
    • 속성이 HTML에 그대로 보이므로 서버 렌더링·부분 하이드레이션 환경에서 JS가 아직 안 붙었어도 버튼이 동작합니다. Next.js처럼 서버 컴포넌트를 많이 쓰는 스택에서 실익이 큽니다.
    • 제약: command/commandfor는 <button>에서만 동작합니다. 링크나 div에는 붙여도 무시됩니다.

    💻 코드

    <!-- 내장 커맨드: show-modal / close / request-close / toggle-popover ... -->

</dialog>
