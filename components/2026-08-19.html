⌨️ OTP 인증번호 입력 입력·폼

문자로 온 6자리 코드를 넣는 그 화면. 사용자가 실제로 겪는 마찰은 세 군데다 — 붙여넣기가 안 됨, 지우려는데 커서가 안 돌아감, SMS 자동입력이 안 뜸. 이 셋을 해결한 칸 분리형과, 자동입력이 가장 잘 붙는 단일 입력형을 나란히 놓았다.

인증번호를 입력하세요

010-****-1234 로 6자리 코드를 보냈습니다. 테스트 코드: 482913

변형 A — 칸 분리형 (segmented)

6자리 인증번호

6칸이 다 차면 자동 제출됩니다. Backspace는 빈 칸에서 앞 칸으로, ←→로 이동, Ctrl/⌘+V로 6자리 한 번에 붙여넣기.

30초 후 재전송할 수 있습니다

변형 B — 단일 입력형 (자동입력 안정성 ↑)

칸을 나누지 않은 입력 하나. 겉보기는 수수하지만 iOS/안드로이드의 SMS 코드 자동입력이 가장 잘 붙는 형태이고, 붙여넣기·스크린리더·비밀번호 관리자와도 충돌이 적다. (칸 분리형은 시각적 만족도가 높은 대신 자동입력이 첫 칸에만 걸리는 경우가 있다 — 추정, 기기·OS별 편차 있음)

🧩 변형들 (요즘 패턴)

  • 붙여넣기 분배 — 어느 칸에 붙여넣든 6자리를 잘라 각 칸에 배분한다. 이게 없으면 사용자는 문자 앱에서 복사해 온 코드를 한 글자씩 다시 친다.
  • 자동 제출(auto-submit) — 마지막 칸이 채워지면 "확인" 버튼을 누르지 않아도 검증을 시작한다. 다만 검증 중임을 문구로 알리고, 실패 시엔 자동 제출을 반복하지 않게 한다.
  • 실패 처리 — 값을 지우고 첫 칸으로 포커스를 되돌린다. 틀린 값을 남겨두면 사용자가 어디를 고쳐야 할지 모른다. 흔들림 애니메이션은 prefers-reduced-motion(사용자가 OS에서 "동작 줄이기"를 켰는지 알려주는 미디어 쿼리)일 때 끈다.
  • 재전송 타이머 — 즉시 재전송을 열어두면 문자 폭탄이 된다. 30초 카운트다운 뒤 활성화하고, 남은 시간을 숫자로 보여준다.
  • 단일 입력형 — letter-spacing으로 자릿수를 시각화하면 칸을 나누지 않고도 "6자리구나"가 읽힌다. 자동입력 신뢰도를 최우선으로 둘 때의 선택.

💻 코드 (복붙용)

<!-- 자동입력 힌트: 첫 칸(또는 단일 입력)에만 one-time-code -->
<input type="text" inputmode="numeric" autocomplete="one-time-code"
       maxlength="1" aria-label="1번째 자리" />

// 붙여넣기 6자리 분배 + 백스페이스 되돌아가기
cells.addEventListener('paste', (e) => {
  const digits = (e.clipboardData.getData('text') || '').replace(/\D/g, '').slice(0, 6);
  if (!digits) return;
  e.preventDefault();
  [...cells.querySelectorAll('input')].forEach((el, i) => { el.value = digits[i] ?? ''; });
  const next = Math.min(digits.length, 5);
  cells.querySelectorAll('input')[next].focus();
});

cells.addEventListener('keydown', (e) => {
  const el = e.target, i = inputs.indexOf(el);
  if (e.key === 'Backspace' && !el.value && i > 0) { inputs[i-1].focus(); inputs[i-1].value=''; e.preventDefault(); }
  if (e.key === 'ArrowLeft'  && i > 0) inputs[i-1].focus();
  if (e.key === 'ArrowRight' && i < 5) inputs[i+1].focus();
});

♿ 접근성·상태 설계

  • 칸마다 aria-label="3번째 자리". 라벨 없는 6개의 빈 입력은 스크린리더에서 "편집, 편집, 편집…"으로만 읽힌다.
  • 결과 문구는 role="status" aria-live="polite" 영역에. 색(빨강/초록)만으로 성패를 알리지 않는다 — 색각 이상 사용자에겐 안 보인다.
  • inputmode="numeric"은 모바일에서 숫자 키패드를 띄운다. type="number"는 스피너·자동 스크롤 문제 때문에 OTP엔 권장되지 않는다.
  • 재전송 버튼은 대기 중 disabled + 남은 초를 텍스트로 노출. 비활성 이유를 안 알려주는 버튼은 고장으로 보인다.
  • 포커스 링(:focus-visible — 키보드로 이동했을 때만 나타나는 외곽선)을 지우지 않는다.

🧠 paysable 적용 포인트

  • 본인확인 SMS, 카드사 인증, 3DS 추가 인증 — 결제 퍼널에서 OTP는 이탈률이 가장 높은 한 칸이다. 붙여넣기 분배 하나만 넣어도 체감이 크다.
  • 자동 제출 시 버튼 로딩 상태 + 중복 제출 잠금을 반드시. 결제 인증은 중복 호출이 그대로 비용/락으로 이어진다.
  • 실패 횟수 제한이 있다면 "남은 시도 2회"를 숫자로 노출. 갑작스러운 잠금은 CS 문의로 돌아온다.

💳 주소·배송지 입력 폼 결제·체크아웃

체크아웃에서 가장 길고 지루한 구간. 줄일 수 있는 방법은 세 가지뿐이다 — 브라우저 자동완성을 제대로 받아먹기(autocomplete 토큰), 우편번호 검색으로 두세 칸을 한 번에 채우기, 청구지=배송지 체크 하나로 폼 절반을 접기.

배송지
청구지
청구지 폼이 접혀 있습니다 — 입력 칸 4개가 줄었습니다.

"우편번호 찾기"를 열어 강남 / 판교 / 해운대 같은 키워드를 넣어보세요. 선택하면 우편번호·기본 주소가 채워지고 커서가 상세 주소로 자동 이동하며, 스크린리더에도 "주소가 입력되었습니다"가 읽힙니다.

🧩 변형들 (요즘 패턴)

  • autocomplete 토큰 정확히 쓰기 — name/tel/postal-code/address-line1은 정해진 이름이다. 여기에 shipping/billing 접두어를 붙이면 브라우저가 배송지·청구지를 구분해 채운다. 이름을 틀리면 자동완성이 통째로 죽는다 — 폼 길이를 줄이는 가장 싼 방법인데 가장 자주 빠뜨린다.
  • 검색으로 채우는 칸은 readonly — 우편번호·기본 주소는 직접 타이핑을 막고 검색 결과로만 채운다. 오타 주소가 그대로 배송 실패가 되는 걸 막는다. (disabled가 아니라 readonly여야 폼 전송에 값이 포함된다.)
  • 채운 뒤 포커스 이동 — 검색 모달을 닫으면 사용자가 다음에 할 일은 "동·호수 입력"뿐이다. 거기로 커서를 옮겨준다.
  • 청구지 접기 — 기본값을 "동일함 체크됨"으로. 대부분의 사용자에게 청구지 4칸은 그냥 사라진다. 체크를 풀 때만 펼친다.
  • 자동 채워진 칸 표시 — 초록 테두리로 "내가 안 쳤는데 값이 들어왔다"를 납득시킨다. 색만으로 끝내지 말고 안내 문구를 함께.

<input autocomplete="shipping postal-code"   inputmode="numeric" readonly />

♿ 접근성·상태 설계

  • 모든 입력에 실제 <label for>. placeholder는 라벨이 아니다 — 입력하는 순간 사라져서 "이 칸이 뭐였지"가 된다.
  • 배송지/청구지는 <fieldset><legend>로 묶는다. 스크린리더가 "배송지 그룹, 이름 편집"처럼 맥락을 함께 읽는다.
  • 접는 영역은 hidden 속성으로. CSS display:none만 쓰면 상황에 따라 숨은 칸에 포커스가 들어가는 사고가 난다.
  • 우편번호 검색은 네이티브 <dialog> + showModal() — 포커스 트랩(모달 밖으로 Tab이 새지 않게 가두는 것)과 Esc 닫기를 브라우저가 공짜로 준다.
  • 값이 자동으로 바뀐 사실은 aria-live="polite"로 알린다. 화면을 못 보는 사용자에겐 초록 테두리가 아무 정보도 아니다.

🧠 paysable 적용 포인트

  • 가맹점 등록·정산 계좌 주소 입력 같은 관리 화면에도 그대로 재사용 가능한 구조다. 검색 소스만 실제 주소 API로 갈아끼우면 된다.
  • 청구지 주소는 카드사 AVS(주소 검증)나 해외 결제에서 필요해지는 값이다. "동일함" 기본 체크 + 필요 시 펼치기가 안전한 기본값.
  • readonly 칸이라도 서버 검증은 별도로. 프론트 readonly는 UX 장치이지 보안 장치가 아니다.

🌀 커스터마이즈 가능한 select 트렌드·개념

<select>의 드롭다운 목록은 오랫동안 CSS로 손댈 수 없는 영역이었다. 그래서 다들 div로 콤보박스를 새로 만들었고, 키보드·스크린리더 대응을 매번 다시 짰다. appearance: base-select는 그 목록을 CSS가 만질 수 있는 영역으로 끌어내려, 네이티브 select 그대로 아이콘·설명·체크마크·애니메이션을 넣게 해준다.

기존 — 네이티브 select

드롭다운 목록은 OS가 그린다. 폰트·색·아이콘 전부 불가.

base-select — 목록까지 내 CSS로

아이콘 + 부제 + 체크마크 + 열림 애니메이션. 그런데도 여전히 진짜 <select> — 키보드 화살표·타이핑 점프·폼 전송·스크린리더가 전부 그대로 동작한다.

지원 여부 확인 중…

📈 왜 지금 뜨나 / 어디에 쓰나

  • 직접 만든 드롭다운의 비용이 컸다 — div 콤보박스는 role="listbox", aria-activedescendant, 포커스 관리, 모바일 스크롤 잠금까지 직접 짜야 하고, 대부분 어딘가 하나는 어긋난다.
  • 동작은 브라우저, 모양은 나 — select와 ::picker(select)(드롭다운 패널을 가리키는 새 가상 요소)에 appearance: base-select를 주면 OS 위젯 대신 브라우저가 그리는 스타일 가능한 팝업이 뜬다. option 안에 <span>·아이콘 같은 진짜 HTML을 넣을 수 있다.
  • 새로 생긴 훅들 — <selectedcontent>(선택된 옵션의 내용을 닫힌 버튼에 그대로 비춰주는 요소), ::picker-icon(화살표), option::checkmark(체크 표시), select:open(열린 상태). 이것들로 열림 회전·페이드까지 CSS만으로 처리된다.
  • 지원 현황(2026-08 기준) — Chromium 계열(Chrome/Edge 135+)에 정식 탑재, Safari는 Technology Preview 단계, Firefox는 Nightly 플래그 뒤에서 구현 중으로 보고돼 있다. 즉 지금은 점진적 향상(progressive enhancement)으로만 쓴다 — 지원하면 예쁜 목록, 아니면 평범한 네이티브 목록. 어느 쪽이든 기능은 멀쩡하다.
  • 안 어울리는 곳 — 옵션이 수백 개고 검색이 필요한 경우는 여전히 콤보박스(자동완성) 영역이다. base-select는 "선택지가 10개 안쪽이고 각 항목에 설명·아이콘을 붙이고 싶은" 케이스에 맞는다.

💻 코드 (복붙용)

/* 1) select와 드롭다운 패널을 모두 base 모드로 */
select, ::picker(select) { appearance: base-select; }

/* 2) 이제 목록이 내 CSS 대상이 된다 */
::picker(select){
  border:1px solid var(--border); border-radius:12px; padding:6px;
  background:var(--surface); box-shadow:var(--shadow);
  opacity:0; transform:translateY(-6px);
  transition:opacity .18s, transform .18s, overlay .18s allow-discrete, display .18s allow-discrete;
}
select:open::picker(select){ opacity:1; transform:translateY(0); }
@starting-style { select:open::picker(select){ opacity:0; transform:translateY(-6px);} }

option{ display:flex; align-items:center; gap:11px; padding:9px 10px; border-radius:9px; }
option:checked{ background:var(--brand-soft); font-weight:600; }
option::checkmark{ order:99; margin-left:auto; color:var(--brand); }
select::picker-icon{ margin-left:auto; transition:transform .2s; }
select:open::picker-icon{ transform:rotate(180deg); }

<!-- 3) 닫힌 상태 버튼 + selectedcontent (선택값이 그대로 비침) -->
<select>
  <button type="button"><selectedcontent></selectedcontent></button>
  <option value="card"><span>💳</span><span>신용·체크카드</span></option>
</select>

♿ 접근성·상태 설계

  • 가장 큰 이점이 접근성이다. 화살표 이동, 글자 타이핑으로 항목 점프, Enter/Esc, 폼 전송, 스크린리더 역할 — 전부 브라우저 기본 동작을 그대로 물려받는다. 직접 만든 드롭다운이 늘 놓치던 부분이다.
  • option 안에 넣은 내용은 그대로 읽힌다. 아이콘 이모지가 소리로 읽혀 방해되면 aria-hidden="true"를 붙인다.
  • :focus-visible 외곽선은 select에 직접 준다. base 모드에선 OS가 그려주던 포커스 표시가 사라질 수 있다.
  • 열림 애니메이션은 prefers-reduced-motion에서 끈다.
  • 미지원 브라우저에서 appearance: base-select는 그냥 무시되고 평범한 select가 된다. 이게 이 기능을 지금 써도 되는 이유다.

🧠 paysable 적용 포인트

  • 결제 수단 선택처럼 항목마다 로고·수수료·설명이 붙는 드롭다운이 정확히 이 기능의 표적이다. 지금 커스텀 콤보박스로 짜여 있다면, 라이브러리 의존을 한 겹 걷어낼 후보.
  • 지원 브라우저 비중이 관리자 화면(사내 Chrome 위주)과 고객 결제 화면(모바일 Safari 다수)에서 크게 다르다. 관리자/백오피스부터 먼저 도입하는 게 위험이 적다.
  • 도입 시 @supports (appearance: base-select)로 감싸 스타일을 분기하면, 미지원 환경의 레이아웃 사고를 원천 차단할 수 있다.
