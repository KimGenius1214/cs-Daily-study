🪟 파괴적 액션 확인 — 되돌리기·확인창·타이핑 확인 오버레이·모달

"정말 삭제하시겠습니까?" 하나로 모든 위험한 버튼을 막는 시대는 지났다. 요즘은 되돌릴 수 있으면 안 묻고, 되돌릴 수 없을 때만 묻되 위험도에 따라 마찰(friction)을 달리 준다. 마찰이란 사용자가 실수하지 못하게 일부러 넣는 한 단계의 수고를 말한다.

위험도 3단계를 각각 다르게 처리한 실제 데모

  • 가맹점 메모 되돌리기 가능 지우고 5초 안에 되살릴 수 있다 · 확인창 없음
  • 정산 계좌 (국민 ****3182) 확인 필요 되돌릴 수 없다 · 표준 확인 다이얼로그
  • 가맹점 계정 «블루보틀 성수» 복구 불가 거래·정산 이력까지 사라진다 · 이름을 직접 입력해야 실행
아직 아무 것도 지우지 않았습니다.

셋 다 Tab·Esc로 조작해 보세요. 다이얼로그가 닫히면 포커스가 눌렀던 버튼으로 되돌아갑니다. 되돌리기 토스트는 5초 뒤 사라집니다.

변형 비교 — 언제 뭘 쓰나

패턴언제설계 포인트
확인 없음 + 되돌리기 기본값 서버에서 복원 가능하거나, 실수해도 손해가 적을 때 (메모·라벨·필터 삭제) 즉시 실행하고 토스트로 실행취소 제공. 확인창보다 클릭이 한 번 적고, 실수한 소수만 되돌린다.
표준 확인 다이얼로그 되돌릴 수 없을 때 복구 불가하지만 영향 범위가 한정적일 때 (결제수단·계좌·API 키 삭제) 제목에 대상 이름을 박고, 버튼 라벨을 "확인"이 아니라 "계좌 삭제"처럼 동사로. 기본 포커스는 안전한 쪽(취소).
타이핑 확인 최고 위험 연쇄 삭제·되돌릴 수 없는 대량 데이터 (가맹점 계정, 저장소 삭제) 대상 이름을 정확히 입력해야 실행 버튼이 열린다. 사용자가 "무엇을" 지우는지 한 번 더 읽게 만드는 게 목적.
카운트다운 비활성 비권장 — "3초 뒤 활성화"는 읽게 만들지 못하고 기다리게만 한다. 인지 부하 대신 대기 시간만 늘어 추천하지 않는다.

💻 핵심 코드

<!-- 네이티브 dialog: showModal()이 배경 비활성화·포커스 트랩·Esc를 다 해준다 -->
<dialog id="cfm" aria-labelledby="cfmTitle">
  <h3 id="cfmTitle">정산 계좌를 삭제할까요?</h3>
  <p>국민 ****3182 · 되돌릴 수 없습니다.</p>
  <form method="dialog">
    <!-- 기본 포커스는 '안전한' 취소에. autofocus를 위험 버튼에 주지 않는다 -->
    <button value="cancel" autofocus>취소</button>
    <button value="confirm" class="danger">계좌 삭제</button>  <!-- 라벨은 동사 -->
  </form>
</dialog>

const trigger = e.currentTarget;
cfm.showModal();
cfm.addEventListener('close', () => {
  if (cfm.returnValue === 'confirm') remove();
  trigger.focus();          // 닫히면 눌렀던 버튼으로 포커스 복귀
}, { once:true });

♿ 접근성·상태 설계

  • showModal()은 show()와 다르다. 모달로 열어야 배경이 inert(포커스·클릭이 통하지 않는 상태)가 되고 Esc가 먹는다.
  • aria-labelledby로 다이얼로그 제목을 연결한다. 스크린리더가 열리는 순간 "무엇에 대한 창인지" 읽어준다.
  • autofocus는 파괴적 버튼에 주지 않는다. Enter 연타로 실수 삭제가 일어난다.
  • 닫힌 뒤 포커스를 트리거로 되돌린다. 안 그러면 키보드 사용자가 문서 맨 위로 튕겨나간다.
  • 배경 클릭으로 닫는 기능(light dismiss)은 closedby="any"로 선언할 수 있다. 단 파괴적 확인창에는 쓰지 않는다 — 실수로 눌러 닫히면 안 되는 창이다.
  • 토스트의 실행취소 버튼은 키보드로 도달 가능해야 하고, 자동 닫힘 시간(5초 이상) 안에 닿을 수 있어야 한다. 로그는 aria-live="polite"로 결과를 알린다.
paysable 적용: 결제수단 삭제·정기결제 해지처럼 돈이 걸린 액션은 "확인" 버튼 라벨을 반드시 "정기결제 해지"처럼 결과를 말하는 동사로 바꾼다. 반대로 필터·메모·즐겨찾기 삭제는 확인창을 없애고 실행취소 토스트로 돌리면 클릭 수가 줄고 체감 속도가 올라간다.

🔔 폼 제출 에러 요약 — 여러 곳이 틀렸을 때 어디로 데려갈까 피드백·상태

필드 5개 중 3개가 틀렸는데 화면 아래쪽 필드 옆에만 빨간 글씨가 뜨면, 사용자는 스크롤해서 찾아다녀야 한다. 요즘 접근성 가이드가 권하는 방식은 폼 맨 위 에러 요약 + 각 필드 인라인 에러를 함께 두고, 제출 실패 시 요약 상자로 포커스를 옮기는 것이다.

일부러 틀리게 제출해 보세요 (빈 칸으로 그냥 제출해도 됩니다)

입력을 확인해 주세요

    ✅ 결제 정보가 저장되었습니다.

    제출하면 요약 상자로 포커스가 이동하고, 목록의 링크를 누르면 그 필드로 바로 점프합니다. 한 번 틀린 뒤부터는 입력하는 즉시 다시 검증되어 에러가 사라집니다.

    검증 타이밍 — 이게 절반이다

    시점무엇을 할까
    타이핑 중 (첫 시도) 아무 말도 하지 않는다. 이메일 두 글자 쳤는데 "형식이 올바르지 않습니다"가 뜨면 훈계로 느껴진다.
    포커스가 빠질 때 (blur) 그 필드만 조용히 검증. 값이 비어 있으면 아직 안 건드린 것으로 보고 넘어가도 된다.
    제출 시 전체 검증 → 요약 상자 표시 → 요약으로 포커스 이동. 첫 에러 필드로 바로 보내는 방식도 있지만, 요약이 "몇 개가 왜 틀렸는지"를 먼저 알려줘 더 낫다.
    제출 실패 후 재입력 즉시 재검증으로 바꾼다. 이미 틀린 걸 아는 상태라 실시간 피드백이 도움이 된다. (이 전환을 흔히 "정정 모드"라 부른다)

    💻 핵심 코드

    <!-- 요약 상자: 포커스를 받을 수 있게 tabindex="-1", 낭독을 위해 role="alert" -->
<div class="summary" id="errSummary" tabindex="-1" role="alert">
  <h4>입력을 확인해 주세요</h4>
  <ol><li><a href="#card">카드 번호는 숫자 15~16자리여야 합니다</a></li></ol>
</div>

function showErrors(errors){
  errors.forEach(({id, msg}) => {
    const input = document.getElementById(id);
    input.setAttribute('aria-invalid', 'true');        // 스크린리더에 "오류 상태"
    document.getElementById('e-' + id).textContent = msg; // aria-describedby로 연결된 칸
  });
  summary.classList.add('on');
  summary.focus();          // ← 핵심. 제출 실패 위치를 사용자에게 "데려다준다"
  submitted = true;         // 이후부터는 input 이벤트로 실시간 재검증
}

    ♿ 접근성·상태 설계

    • aria-describedby로 입력칸과 에러 문구를 이어 붙인다. 이러면 스크린리더가 필드에 들어갈 때 에러 문구까지 읽어준다.
    • aria-invalid="true"는 색으로만 전하던 "틀림"을 보조기기에도 전한다 — 빨간 테두리만으로는 색각 이상 사용자에게 전달되지 않는다. 다만 에러 문구를 이미 aria-describedby로 읽어주고 있다면 중복 낭독이라 오히려 장황하다는 반론도 있다(GOV.UK Design System에서 논의 중인 쟁점). 둘 중 하나는 반드시 있어야 한다는 점이 핵심.
    • 에러 메시지는 무엇이 틀렸는지 + 어떻게 고치는지를 함께. "올바르지 않습니다"(✗) → "숫자 15~16자리로 입력해 주세요"(✓)
    • 요약 목록의 링크는 href="#필드id"로 두면 마우스·키보드 모두 그 필드로 점프한다.
    • 에러 요약을 두 번째 제출에서 다시 띄울 때는 내용을 지웠다가 다시 채워야 role="alert"가 재낭독된다.
    • novalidate로 브라우저 기본 말풍선을 끄고 직접 그리는 이유: 기본 말풍선은 한 번에 하나만 뜨고 스타일을 못 바꾼다.
    paysable 적용: 결제 폼은 실패 한 번이 곧 이탈이다. 카드 승인 거절 같은 서버 에러도 같은 요약 상자에 합류시키면(예: "카드사에서 거절했습니다 — 다른 카드로 시도해 주세요") 사용자는 한 곳만 보면 된다. 체크아웃처럼 필드가 긴 화면일수록 요약의 이득이 크다.

    🌀 @starting-style와 allow-discrete — 사라졌다 나타나는 것도 부드럽게 트렌드·개념

    오랫동안 CSS의 골칫거리였던 문제: display:none이던 요소를 보이게 하면 애니메이션이 안 걸린다. 브라우저는 방금 나타난 요소의 "이전 상태"를 모르기 때문이다. 그래서 다들 JS로 클래스를 두 번 나눠 붙이거나 라이브러리를 썼다. 이걸 CSS 두 조각이 해결한다 — @starting-style(시작값을 알려주는 규칙)과 transition-behavior: allow-discrete(display처럼 중간값이 없는 속성도 전환 대상에 넣기).

    블루보틀 성수 · 4,800원

    적용 상태 — 열 때도 닫을 때도 0.3초에 걸쳐 부드럽게 이어집니다.

    스위치를 끄면 똑같은 transition 선언이 걸려 있는데도 열림이 툭 튀고, 닫힘은 즉시 사라집니다. 진입에는 @starting-style이, 퇴장에는 allow-discrete가 각각 필요하기 때문입니다.

    popover와 함께 — 백드롭까지 같이 페이드

    다른 결제수단

    등록된 카드가 3장 있습니다. 백드롭(뒤 어두운 막)도 함께 서서히 나타나고 사라집니다.

    [popover]는 열릴 때 브라우저가 최상위 레이어(top layer)로 올린다. 그래서 사라질 때 overlay라는 속성도 allow-discrete로 같이 전환해 줘야 "레이어에서 먼저 빠지고 나서 페이드"되는 어색함이 없다.

    💻 핵심 코드 (복붙용)

    .pop {
  display: none;                     /* 닫힌 상태 */
  opacity: 0;
  transform: translateY(10px) scale(.96);
  transition:
    opacity   .3s ease,
    transform .3s cubic-bezier(.2,.8,.2,1),
    display   .3s allow-discrete,    /* ← 퇴장: display:none을 끝까지 미룬다 */
    overlay   .3s allow-discrete;    /* ← top layer 요소(popover/dialog)일 때 필요 */
}
.pop.open { display: block; opacity: 1; transform: none; }

/* ← 진입: "나타나기 직전"의 값. 이게 없으면 첫 프레임에 이미 최종값이라 전환이 안 생긴다 */
@starting-style {
  .pop.open { opacity: 0; transform: translateY(10px) scale(.96); }
}

/* 한 줄 요약 축약형도 가능 */
.pop { transition: all .3s allow-discrete; }

    📈 왜 지금 뜨나 / 어디에 쓰나

    • web.dev 발표 기준 2024년 8월 6일 Baseline "newly available"에 올랐다 — 크롬·엣지 117+, 사파리 17.5+, 파이어폭스 129+에서 동작한다. 2026년 현재는 실무 투입에 무리 없는 수준으로 본다.
    • 같은 시기에 <dialog>·popover가 널리 퍼지면서 "열고 닫는 UI"를 CSS만으로 완결할 수 있게 됐다. 애니메이션 때문에 남겨두던 JS 상태 플래그를 지울 수 있다.
    • 애니메이션 라이브러리(Framer Motion 등)를 모달 하나 때문에 번들에 넣던 관행을 줄인다. 리스트 전환에는 여전히 View Transitions가, 진입·퇴장에는 이쪽이 맞다.
    • 미지원 브라우저에서는 전환만 사라지고 열림·닫힘 자체는 정상이다. 즉 점진적 향상(progressive enhancement)으로 안전하게 얹을 수 있다.
    • 주의: @starting-style은 이미 화면에 있던 요소의 일반 상태 변화에는 필요 없다. "없다가 생기는" 순간에만 쓴다.
    paysable 적용: 결제 확인 시트·토스트·툴팁 같은 짧게 떴다 사라지는 UI 전부가 대상이다. 특히 닫힘 애니메이션은 지금까지 "닫기 클래스 붙이고 300ms 뒤에 언마운트" 같은 setTimeout으로 처리하던 부분인데, allow-discrete를 쓰면 그 타이머를 지울 수 있다. React라면 조건부 렌더링({open && ...}) 대신 항상 렌더하고 클래스만 토글하는 구조로 바꿔야 효과가 난다.
