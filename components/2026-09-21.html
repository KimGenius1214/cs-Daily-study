🔘 링크냐 버튼이냐 — 똑같이 생겼는데 능력이 다르다 버튼·액션

디자인 시스템이 성숙할수록 링크도 버튼처럼 생긴다. 그 순간부터 "무엇으로 만들었나"는 눈에 안 보이지만, 사용자 손에는 그대로 드러난다. 가운데 클릭, Ctrl+클릭, 우클릭 메뉴, Space 키 — 이게 되냐 안 되냐가 요소 선택으로 결정된다.

변형 1 — 같은 모양, 다른 능력

3개 모두 CSS가 동일합니다. 눌러보고 · Tab으로 지나가 보고 · 가운데 버튼으로도 눌러보세요

정산 내역 보기 <a href>
정산 새로고침 <div onclick>
a href button div onclick

위 칩은 Tab으로 실제 포커스가 닿은 요소를 초록으로 칠합니다. div는 영원히 회색입니다.

같은 픽셀이라도 <a href>는 브라우저가 "주소가 있는 것"으로 알기에 새 탭·주소 복사·미리보기가 공짜로 따라온다. <button>은 Space/Enter 양쪽에 반응하고 form과 연결된다. <div>는 아무것도 없다.

변형 2 — form 안의 버튼은 기본이 submit이다

입력칸에서 Enter를 쳐보고, 아래 두 버튼도 눌러보세요

첫 버튼의 현재 타입: type 없음 → submit으로 동작

HTML 기본값은 type="submit"이다. form 안에서 타입을 안 쓴 버튼은 전부 제출 버튼이라, "검색" 버튼이 결제 폼을 제출해버리는 사고가 여기서 난다. 또한 텍스트 입력이 하나라도 있으면 Enter만으로 암묵적 제출이 일어난다.

변형 3 — 고르는 기준 한 줄

하려는 일고를 것이유
다른 주소로 이동한다<a href> (Next.js면 <Link>)주소가 있다 = 공유·새 탭·뒤로가기가 성립
같은 화면에서 무언가를 일으킨다<button type="button">주소가 없다 = 링크가 아니다
폼을 보낸다<button type="submit">Enter 암묵적 제출까지 자동 연결
파일을 내려받는다<a href download>브라우저 다운로드 UI·재시도가 공짜
모달·팝오버를 연다<button commandfor>Invoker Commands로 JS 없이 (지원 브라우저에서)
지금은 못 누르게 한다버튼이면 aria-disabled, 링크면 렌더하지 않기비활성 링크는 표준 개념이 없다
안티패턴 3종 — ① <a>에 href 없이 onClick만 (포커스·역할 사라짐) ② <a href="#"> + preventDefault (주소가 거짓말) ③ <button>을 router.push로 감싸기 (새 탭·주소 복사가 죽음). React에서 카드 전체를 누르게 만들 땐 <a>를 덮고 내부 버튼을 stopPropagation으로 살리는 쪽이 안전하다.

💻 복붙용

// ❌ 링크인데 버튼으로 만들어서 새 탭·주소 복사를 잃는다
<button onClick={() => router.push(`/settlements/${id}`)}>정산 상세</button>

// ✅ 주소가 있으면 링크로. 새 탭·⌘클릭·우클릭이 전부 공짜로 따라온다
<Link href={`/settlements/${id}`} className="btn">정산 상세</Link>

// ✅ 주소가 없으면 버튼으로. form 안이면 type을 반드시 적는다
<form onSubmit={onSubmit}>
  <input name="q" />
  <button type="button" onClick={reset}>초기화</button>   {/* 생략하면 submit! */}
  <button type="submit">검색</button>
</form>

// ✅ 다운로드는 링크가 맡는다 (진행률·재시도를 브라우저가 처리)
<a href={receiptUrl} download={`영수증-${id}.pdf`} className="btn">영수증 내려받기</a>
용어 한 줄 — 암묵적 제출(implicit submission): 텍스트 입력이 있는 form에서 Enter만 눌러도 제출이 일어나는 HTML 기본 동작. stopPropagation: 이벤트가 부모로 타고 올라가는 걸 그 지점에서 멈추는 것.

⌨️ 한글 입력과 IME — 조합 중인 글자는 아직 "값"이 아니다 입력·폼

한글·일본어·중국어는 IME(Input Method Editor, 조합 입력기)를 거친다. 자판을 두드리는 동안 글자는 "조합 중" 상태로 입력칸에 미리 보이지만 아직 확정된 값이 아니다. 영문만 놓고 만든 검색·검증·Enter 처리가 한국 사용자에게만 깨지는 이유가 전부 여기 있다.

변형 1 — 조합 중에 무슨 이벤트가 오는지 직접 보기

한글 자판으로 "안녕"을 천천히 쳐보세요 (영문도 쳐보면 차이가 보입니다)

조합 중: 아니오 화면 값 길이: 0 확정된 값 길이: 0

순서는 compositionstart → compositionupdate(자모마다) → compositionend(확정). keydown에는 isComposing: true가 붙어 있고, 레거시 브라우저에선 keyCode === 229로 나타난다. 즉 입력칸에 글자가 보여도 아직 확정이 아닐 수 있다.

변형 2 — Enter 한 번이 두 번으로 세어지는 버그

양쪽에 한글로 "결제"를 치고 Enter를 한 번만 누르세요

❌ 가드 없음

0

✅ isComposing 가드

0

조합을 확정하는 Enter와 "검색 실행" Enter는 같은 키 한 번이다. 가드가 없으면 조합 확정용 Enter까지 실행으로 세어져 조회가 두 번 나간다. 결제 화면이라면 이게 중복 제출이 된다.

영문 자판에서는 조합이 없어 양쪽이 똑같이 1로 보인다. 이 버그는 한글 자판으로만 재현된다 — 영어권 라이브러리에 이 이슈가 계속 올라오는 이유.

변형 3 — 조합 중엔 조회도 검증도 미룬다

가맹점 검색: 조합 중에는 서버를 때리지 않고, 확정된 뒤에만 300ms 디바운스로 조회합니다

서버 호출 횟수: 0 상태: 대기

디바운스(debounce): 입력이 멎고 일정 시간이 지난 뒤에만 실행하는 기법. 여기에 조합 가드를 더하면 "ㄱ → 가 → 간 → 감" 같은 중간 자모로 헛조회하는 일이 사라진다.

함께 깨지는 것들 (체크리스트)

  • 글자수 카운터 / maxlength — 조합 중 중간 글자까지 세어 "10/10"이 됐다가 확정하면 9가 된다. 확정 기준으로 세는 게 안전하다(추정: 브라우저·IME별 편차 있음).
  • 자동 포맷 입력 — 조합 중에 값을 가공해 setState하면 조합이 강제로 끊기고 글자가 깨진다. 금액·전화번호 포맷팅은 compositionend 뒤에.
  • controlled input — React에서 조합 중 value를 덮어쓰면 "한글이 거꾸로 써지는" 증상이 난다. 조합 중엔 DOM 값을 그대로 두자.
  • 즉시 검증 — 조합 중 "형식이 올바르지 않습니다"가 깜빡인다. 검증은 blur 또는 확정 후로.

💻 복붙용

// ✅ Enter 중복 제출 가드 (React)
// React의 SyntheticEvent에는 isComposing이 없어 nativeEvent로 읽는다.
// keyCode 229는 구형 Safari·일부 안드로이드 키보드용 레거시 신호.
const onKeyDown = (e: React.KeyboardEvent<HTMLInputElement>) => {
  if (e.key !== "Enter" || e.shiftKey) return;
  if (e.nativeEvent.isComposing || e.keyCode === 229) return; // 조합 확정용 Enter → 무시
  e.preventDefault();
  submit();
};

// ✅ 조합 가드 + 디바운스 검색 (훅 없이도 되는 최소형)
let composing = false, timer: ReturnType<typeof setTimeout>;
input.addEventListener("compositionstart", () => { composing = true; });
input.addEventListener("compositionend", (e) => { composing = false; schedule(e.currentTarget.value); });
input.addEventListener("input", (e) => {
  if (composing) return;                 // 조합 중 = 아직 확정 아님 → 조회 보류
  schedule((e.currentTarget as HTMLInputElement).value);
});
function schedule(v: string) {
  clearTimeout(timer);
  timer = setTimeout(() => fetchMerchants(v.trim()), 300);
}
⚠️ 미검증 영역 — Safari는 조합 확정 Enter를 compositionend 뒤에 보내서 그 시점엔 isComposing이 이미 false인 경우가 보고된다(그래서 keyCode === 229를 함께 본다). 브라우저·OS·IME 조합마다 순서 차이가 있으므로 실기기에서 한 번은 직접 확인할 것.

🌀 reading-flow — 레이아웃이 어긋뜨린 탭 순서를 CSS가 바로잡는다 트렌드·개념

flex·grid로 순서를 바꿔 배치하면 보이는 순서와 DOM 순서가 갈라진다. 마우스 사용자는 모르지만 Tab 키와 스크린리더는 지금까지 항상 DOM 순서를 따라갔다. reading-flow는 "보이는 대로 읽고 이동하게" 만드는 새 CSS 속성이다.

변형 1 — row-reverse가 만든 지그재그 탭 순서

아래 버튼들은 DOM 순서가 1·2·3·4인데 flex-direction: row-reverse로 화면엔 거꾸로 놓입니다

직접 Tab으로 지나가 보세요. 모드를 바꾸면 이동 경로가 달라집니다(지원 브라우저 한정).

normal일 때 Tab은 화면 오른쪽 → 왼쪽으로 튄다. flex-visual이면 보이는 대로 왼쪽 → 오른쪽. "결제하기"가 세 번째로 읽히느냐 마지막으로 읽히느냐가 여기서 갈린다.

변형 2 — grid + order로 뒤섞은 대시보드

CSS order로 재배치한 카드들. reading-flow: grid-order는 그 순서를 탭 순서로도 인정합니다

지금까지 이런 화면의 해법은 "DOM을 시각 순서대로 다시 쓰고 CSS로 되돌리기"였다. reading-flow는 그 뒤틀기를 없애준다.

📈 왜 지금 뜨나 / 무엇을 조심하나

  • 값 — normal(기본) / flex-visual / flex-flow / grid-rows / grid-columns / grid-order / source-order. 형제 하나만 끼워 옮길 땐 reading-order(숫자)를 쓴다.
  • 지원(2026-09 기준 조사) — Chrome 137부터, Safari 26.4부터 지원. Firefox는 아직 플래그 뒤. Baseline 아님.
  • 안전한 이유 — 모르는 브라우저는 그냥 DOM 순서를 쓴다. 즉 점진적 향상이라 깨지지 않는다. 다만 "지원 브라우저에서만 올바른 순서"가 되므로, DOM 순서 자체를 말이 되게 짜는 원칙은 그대로 유효하다.
  • 남용 주의 — 시각 순서를 마구 뒤집어도 된다는 허가증이 아니다. 반응형에서 한 곳만 어쩔 수 없이 어긋날 때 쓰는 보정 도구로 보는 게 맞다.

/* 모바일에선 CTA를 위로 올리되, 탭 순서는 보이는 대로 따라오게 */
.checkout-actions {
  display: flex;
  flex-wrap: wrap;
  reading-flow: flex-visual;   /* 미지원 브라우저는 DOM 순서 유지 */
}
@media (max-width: 640px) {
  .checkout-actions .primary { order: -1; }
}

/* 형제 하나만 순서를 끼워 넣기 */
.summary-card { reading-flow: grid-rows; }
.summary-card .alert { reading-order: -1; }  /* 경고를 제일 먼저 읽게 */

/* 지원 여부로 분기하고 싶다면 */
@supports (reading-flow: flex-visual) {
  .checkout-actions { /* 지원 브라우저 전용 미세조정 */ }
}
용어 한 줄 — 점진적 향상(progressive enhancement): 지원하는 브라우저에선 더 좋아지고, 지원 안 하는 브라우저에서도 기본 동작은 그대로인 방식. Baseline: 주요 브라우저에 모두 도달했는지를 표시하는 웹 플랫폼 기준.
