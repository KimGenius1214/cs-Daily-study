🧭 넘치는 탭 처리 내비게이션·탭

탭이 6개일 땐 아무 문제가 없다가, 가맹점이 늘어 12개가 되면 탭바가 화면 밖으로 삐져나간다. 해결책은 세 가지뿐이다 — 가로로 스크롤시키거나, 안 들어가는 걸 “더보기” 메뉴로 접거나, 좁은 화면에선 아예 select로 바꾸거나. 어느 쪽을 고르든 키보드 동작은 똑같이 지켜야 한다.

880px

변형 A — 가로 스크롤 탭바 (화살표 + 스크롤 그림자)

탭을 ← → 로 옮기면 선택된 탭이 자동으로 화면 안으로 스크롤된다. 양 끝의 흐릿한 그라데이션은 “이쪽에 더 있다”는 유일한 단서 — 이게 없으면 사용자는 스크롤될 수 있다는 걸 모른다.

변형 B — 안 들어가는 탭을 “더보기(⋯)” 메뉴로 접기

    폭 슬라이더를 줄여보면 오른쪽 탭들이 하나씩 ⋯ 메뉴로 들어간다. 지금 선택된 탭은 절대 숨기지 않는다 — 숨기면 “내가 어디 있는지”가 사라진다. 메뉴 안의 항목을 고르면 그 탭이 앞으로 나온다.

    변형 C — 아주 좁을 땐 select 폴백

    탭이 12개인데 폭이 300px이면 스크롤도 메뉴도 다 불편하다. 이때는 네이티브 select가 가장 빠르다 — 모바일에선 OS가 알아서 큰 목록 UI를 띄워준다. 화려함을 포기하고 속도를 얻는 선택.

    role 정리 — 탭바는 role="tablist", 각 탭은 role="tab" + aria-selected, 내용은 role="tabpanel". 선택 안 된 탭은 tabindex="-1"로 빼서 Tab 한 번에 탭바를 건너뛰게 하고, 탭 사이 이동은 화살표로 한다(roving tabindex = 포커스 가능한 항목을 한 번에 하나만 두는 기법).

    💻 핵심 코드 — roving tabindex + 선택 탭 자동 스크롤

    list.addEventListener('keydown', (e) => {
  const tabs = [...list.querySelectorAll('[role=tab]')];
  const i = tabs.indexOf(document.activeElement);
  const next = { ArrowRight: i + 1, ArrowLeft: i - 1, Home: 0, End: tabs.length - 1 }[e.key];
  if (next === undefined) return;
  e.preventDefault();
  const t = tabs[(next + tabs.length) % tabs.length];   // 끝에서 반대편으로 순환
  select(t);
  t.focus();
  // 선택된 탭이 잘려 있으면 보이는 곳까지 밀어준다
  t.scrollIntoView({ inline: 'nearest', block: 'nearest',
                     behavior: matchMedia('(prefers-reduced-motion: reduce)').matches ? 'auto' : 'smooth' });
});

    inline:'nearest'가 핵심 — 이미 보이면 안 움직이고, 잘려 있을 때만 최소한으로 민다.

    ♿ 접근성·상태 설계

    • 선택 탭은 접지 않는다. 더보기 메뉴에 현재 탭이 들어가면 사용자는 현 위치를 잃는다.
    • 화살표 버튼은 보조 수단. 터치·트랙패드 사용자는 그냥 밀면 되므로, 화살표가 없어도 스크롤은 동작해야 한다.
    • 끝에 닿으면 화살표를 disabled 처리해 “더 없음”을 알린다(그냥 회색만 칠하지 말고 실제로 비활성화).
    • prefers-reduced-motion(= 사용자가 OS에서 “동작 줄이기”를 켠 상태)이면 부드러운 스크롤을 끄고 즉시 점프.
    • 탭 배지 숫자는 aria-label에 함께 넣어 “미정산 3건”처럼 읽히게 한다.

    🧠 paysable 적용 포인트

    • 가맹점·PG사·정산주기처럼 개수가 데이터에 따라 변하는 탭은 반드시 넘침 대비가 필요하다. 디자인 시안은 늘 6개짜리다.
    • 탭 개수가 8개를 넘어가면 탭이 아니라 select나 좌측 목록이 맞는 신호일 수 있다 — 탭은 “한눈에 비교되는 소수”용.
    • 결제 상세처럼 탭 내용이 무거우면, 탭 전환 시 이전 패널을 지우지 말고 이미 불러온 패널은 유지해 왕복 비용을 없앤다.

    🃏 가상 스크롤 리스트 카드·리스트

    정산 내역 1만 건을 그대로 그리면 DOM 노드가 수만 개가 되고, 스크롤이 끊기고 메모리가 튄다. 가상 스크롤(windowing) = 전체 높이만 가짜로 만들어 두고 실제로는 화면에 보이는 30줄만 그리는 기법. 오늘은 JS로 직접 만든 버전과, CSS 한 줄로 비슷한 효과를 내는 content-visibility 버전을 나란히 본다.

    변형 A — 직접 만든 가상 스크롤 (1만 건)

    DOM 행 수 0 마지막 렌더 0ms 전체 10,000건
    #거래처정산액

    체크를 끄면 1만 행을 전부 그린다 — DOM 행 수와 렌더 시간이 어떻게 달라지는지 위 숫자를 보라. 스크롤 감촉도 직접 비교해 볼 것. (기기에 따라 끄면 잠깐 멈출 수 있다)

    변형 B — CSS만으로: content-visibility: auto

    행은 800개 전부 DOM에 있지만, 브라우저가 화면 밖 행의 레이아웃·페인트를 건너뛴다. contain-intrinsic-size로 “안 그린 행도 52px는 차지한다”고 알려줘야 스크롤바가 안 튄다. JS가 필요 없고 Ctrl+F 페이지 검색도 살아 있는 게 장점.

    지원 여부 확인 중…
    어느 쪽을 쓰나 — 행이 수백~2천 개면 content-visibility로 충분하다(코드가 거의 없다). 수만 건이거나 행마다 무거운 컴포넌트가 들어가면 직접 가상화가 필요하다. 직접 가상화는 브라우저 페이지 검색·전체 선택·인쇄가 깨진다는 비용을 반드시 같이 계산해야 한다.

    💻 핵심 코드 — 보이는 구간만 계산해서 그리기

    const ROW = 56, OVERSCAN = 6;             // 행 높이 고정, 위아래 여유분
sizer.style.height = data.length * ROW + 'px';   // 스크롤바 길이는 진짜처럼

function render() {
  const start = Math.max(0, Math.floor(port.scrollTop / ROW) - OVERSCAN);
  const count = Math.ceil(port.clientHeight / ROW) + OVERSCAN * 2;
  const slice = data.slice(start, start + count);

  win.style.transform = `translateY(${start * ROW}px)`;  // 창을 통째로 내려 붙인다
  win.innerHTML = slice.map((d, i) =>
    `<div class="vlrow" role="row" aria-rowindex="${start + i + 1}">…</div>`).join('');
}
port.addEventListener('scroll', () => requestAnimationFrame(render));  // 프레임당 1회로 제한

    requestAnimationFrame으로 감싸는 이유: scroll 이벤트는 1초에 수백 번 오는데, 화면은 초당 60번만 갱신된다. 그 이상 그려봐야 낭비다. 

    /* 변형 B — JS 한 줄도 없는 방식 */
.row {
  content-visibility: auto;          /* 화면 밖이면 렌더링을 건너뛴다 */
  contain-intrinsic-size: auto 52px; /* 안 그린 동안 차지할 높이(auto=한번 잰 값을 기억) */
}

    ♿ 접근성·상태 설계

    • 전체 개수를 미리 알린다. role="grid" + aria-rowcount="10000", 각 행에 aria-rowindex. 이게 없으면 스크린리더는 “목록 30개”라고 잘못 읽는다.
    • 키보드 탈출구. 가상 목록 안은 Tab으로 다 훑을 수 없으므로, 검색·필터·“CSV 내려받기” 같은 다른 경로를 반드시 함께 둔다.
    • 스크롤 위치 복원. 상세로 갔다 돌아오면 scrollTop을 되살려야 한다 — 안 그러면 매번 맨 위.
    • 행 높이가 다를 때는 고정 높이 계산이 무너진다. 측정 후 보정하거나, 높이를 강제로 통일하는 편이 안전하다.
    • overscroll-behavior: contain으로 목록 끝에서 페이지가 같이 밀리는 걸 막는다.

    🧠 paysable 적용 포인트

    • 정산 상세·거래 원장처럼 페이지네이션 없이 통째로 훑고 싶은 화면이 1순위 후보.
    • 다만 결제 도메인은 합계·검증이 중요하다 — 화면에 30줄만 있어도 합계는 전체 기준으로 계산해 상단에 고정 노출.
    • 회계팀은 결국 엑셀로 받는다. 가상 스크롤을 넣더라도 내려받기 버튼이 진짜 주경로일 수 있음을 잊지 말 것.
    • 먼저 content-visibility부터 시도해 보고, 그래도 느릴 때 가상화로 올라가는 순서를 권한다(추정: 대부분의 정산 목록은 전자로 충분).

    🌀 CSS subgrid 트렌드·개념

    카드 4장을 나란히 놓았는데 제목이 한 줄인 카드와 두 줄인 카드가 섞이면 버튼 높이가 제각각이 된다. 지금까지는 제목에 min-height를 박는 눈속임을 썼다. subgrid = 자식 그리드가 자기 격자를 새로 만들지 않고 부모의 격자선을 그대로 물려받는 값. 카드 안쪽 요소들이 부모 행에 직접 붙으니, 카드끼리 줄이 저절로 맞는다.

    행마다 테두리와 배경을 따로 주고 싶은데, 라벨 열 폭은 전체에서 하나로 맞추고 싶은 상황. 각 행을 grid-template-columns: subgrid로 두면 가장 긴 라벨 기준으로 열이 한 번에 정해진다. 표(table)를 쓰지 않고도 표처럼 정렬되는 게 핵심.

    지원 여부 확인 중…

    📈 왜 지금 뜨나 / 어디에 쓰나

    • Firefox가 2019년(71)에 먼저 넣었지만 Chrome·Edge는 2023년 8월(117)에야 따라왔고, 2023-09-15에 세 엔진 모두 지원(Baseline “newly available”)이 됐다. 2026년 3월 “widely available”로 올라섰다. “된 지 오래됐는데 아직 안 쓰는” 대표적인 기능.
    • 지금까지 카드 줄맞춤은 제목에 min-height, 본문에 line-clamp 같은 땜질로 해결했다. 디자인이 바뀌면 그 숫자를 다시 찾아 고쳐야 했다. subgrid는 그 숫자를 없앤다.
    • 컨테이너 쿼리와 짝으로 쓰인다 — 컨테이너 쿼리가 “이 칸 폭에 맞춰 카드 모양 바꾸기”라면, subgrid는 “카드들끼리 줄 맞추기”. 둘 다 부모 폭에 의존하던 계산을 CSS에 넘기는 방향이다.

    💻 코드 (복붙용)

    /* 부모가 행을 정의한다: 제목 / 설명 / 가격 / 버튼 */
.cardgrid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(178px, 1fr));
  grid-template-rows: auto auto auto auto;
  gap: 14px;
}
/* 카드는 그 4행을 통째로 차지하면서 행 정의를 물려받는다 */
.cardgrid > .pcard {
  display: grid;
  grid-row: span 4;
  grid-template-rows: subgrid;
  row-gap: 8px;          /* subgrid는 부모 gap을 자기 값으로 덮어쓸 수 있다 */
}
.cardgrid > .pcard .act { align-self: end; }
    /* 라벨 열 폭 맞추기 */
.paydl { display: grid; grid-template-columns: max-content 1fr; }
.paydl .prow {
  grid-column: span 2;
  display: grid;
  grid-template-columns: subgrid;   /* 부모의 두 열을 그대로 사용 */
  gap: 0 18px;
}

    ♿ 접근성·상태 설계 / 함정

    • subgrid는 레이아웃만 바꾼다. DOM 순서는 그대로이므로 스크린리더 읽기 순서에 영향이 없다 — 이게 장점이다 (반면 order나 grid-row로 시각 순서를 뒤집으면 읽기 순서와 어긋난다).
    • 행 개수가 카드마다 다르면 못 쓴다. 모든 카드가 “제목·설명·가격·버튼” 같은 동일한 슬롯 구조여야 한다. 비어 있는 슬롯은 빈 요소로라도 채워 둔다.
    • span 4의 숫자와 grid-template-rows의 행 수가 어긋나면 조용히 깨진다 — 슬롯 개수를 바꿀 땐 두 곳을 같이 고칠 것.
    • 미지원 브라우저에서는 subgrid 선언이 무시되고 평범한 카드로 보인다(내용은 다 읽힌다). @supports (grid-template-rows: subgrid)로 감싸 폴백 스타일을 분리하면 더 안전하다.

    🧠 paysable 적용 포인트

    • 요금제·결제수단 카드 선택 화면 — “왜 이 카드만 버튼이 아래에 있지?” 버그 리포트가 사라진다.
    • 결제 상세·정산 상세의 라벨·값 목록 — table을 쓸 만큼 표는 아닌데 정렬은 필요한 곳.
    • 기존 코드에서 min-height, height: 100%, flex margin-top:auto 같은 줄맞춤 땜질을 검색해 걷어내는 작업으로 시작하면 효과가 바로 보인다.
