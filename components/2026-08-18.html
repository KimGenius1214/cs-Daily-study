🪟 다단계 모달 위저드 오버레이·모달

입력이 3~4단계로 나뉘는 흐름을 페이지 이동 없이 모달 하나 안에서 처리하는 패턴이다. 핵심은 세 가지 — 단계 진행률을 항상 보여주고, 단계마다 모달 높이가 튀지 않게 부드럽게 바뀌고, 중간에 닫으려 하면 작성 내용을 잃는다고 한 번 확인받는 것.

아직 결제하지 않았습니다.

Esc로 닫기 → 1단계가 아니면 이탈 확인 모달이 뜹니다. Tab은 모달 안에서만 순환(포커스 트랩)하고, 단계가 바뀌면 스크린리더에 "2단계 / 3단계"가 읽힙니다.

🧩 변형들 (요즘 패턴)

  • 진행 바(segmented progress) — 점 3개짜리 막대로 "지금 몇 번째, 몇 개 남음"을 항상 노출. 단계 수를 숨기면 이탈률이 올라간다.
  • 높이 애니메이션 — 단계마다 내용 길이가 달라 모달이 덜컹거리기 쉽다. 다음 화면 높이를 미리 재서(scrollHeight) height를 px로 전환하면 매끄럽다. (또는 아래 3번의 interpolate-size)
  • 이탈 확인(leave confirmation) — 1단계에서 닫으면 그냥 닫고, 2단계 이상에서 닫으면 "작성 중인 내용이 사라집니다" 중첩 확인. 무조건 묻지 않는 게 요점이다.
  • 뒤로 가면 값이 남는다 — 이전 단계로 돌아갔을 때 선택이 초기화되면 신뢰가 깨진다. 상태는 위저드 바깥(폼 state)에 둔다.

💻 코드 (복붙용)

<!-- native dialog: 포커스 트랩·백드롭·Esc가 브라우저 기본 제공 -->
<dialog class="wiz" id="wiz" aria-labelledby="wizTitle">
  <div class="wiz-body" id="wizBody">
    <div class="wiz-pane" id="p1">…</div>
    <div class="wiz-pane" id="p2" hidden>…</div>
  </div>
</dialog>

// 단계 전환 시 높이를 실측해서 전환 (덜컹거림 제거)
function goTo(next) {
  const from = body.offsetHeight;          // 현재 높이 고정
  body.style.height = from + "px";
  panes.forEach((p, i) => p.hidden = i !== next);
  const to = body.scrollHeight;            // 새 내용 높이 실측
  requestAnimationFrame(() => { body.style.height = to + "px"; });
}
body.addEventListener("transitionend", () => { body.style.height = ""; });

// Esc/닫기: 1단계가 아니면 이탈 확인
dlg.addEventListener("cancel", e => {
  if (step > 0) { e.preventDefault(); leaveDlg.showModal(); }
});

♿ 접근성·상태 설계

  • <dialog>.showModal()은 포커스 트랩(탭이 모달 밖으로 안 나감), 배경 inert 처리, Esc 닫기를 브라우저가 알아서 해준다. 직접 구현하지 말 것.
  • 단계 전환 뒤 포커스를 새 단계의 제목(tabindex="-1")으로 옮긴다. 안 그러면 스크린리더 사용자는 화면이 바뀐 걸 모른다.
  • 진행 상태는 aria-live="polite" 영역에 "3단계 중 2단계"로 텍스트 제공. aria-live: 값이 바뀌면 보조기기가 자동으로 읽어주는 영역.
  • 진행 바 자체는 장식이라 aria-hidden="true". 같은 정보를 텍스트로 이미 주고 있으니 중복 낭독을 막는다.
  • 높이 전환은 prefers-reduced-motion에서 끈다. prefers-reduced-motion: 사용자가 OS에서 "동작 줄이기"를 켠 상태.

결제 수단 선택 → 금액·수수료 확인 → 인증 같은 흐름을 페이지 라우팅으로 쪼개면 뒤로가기·새로고침에서 상태가 날아간다. 모달 위저드로 묶되, 단계 인덱스를 URL 쿼리(?step=2)에 반영하면 브라우저 뒤로가기와도 맞물린다. 이탈 확인은 "카드번호를 이미 입력한 단계"부터만 띄워서 마찰을 최소화하고, 마지막 완료 단계에서는 이탈 확인을 끄는 게 맞다(이미 승인이 끝났으므로).

🔔 재시도·백오프 UI 피드백·상태

네트워크나 PG 응답이 한 번 실패했다고 곧장 "오류가 발생했습니다"를 띄우는 건 요즘 기준으로 성의 없는 UI다. 자동으로 몇 번 다시 시도하되 그 사실을 사용자에게 보이고, 간격을 점점 늘리고(지수 백오프), 그래도 안 되면 수동 재시도와 대안을 준다.

결제 승인 요청
신한카드 ****1234 · 주문 #A-20826
₩ 47,000
– 대기 중아래 버튼을 눌러 승인을 요청하세요.

    자동 재시도는 최대 3회, 간격은 2초 → 4초로 늘어납니다(지수 백오프). 카운트다운 중에도 "지금 재시도"로 건너뛰거나 "취소"할 수 있고, 3회 모두 실패하면 자동 반복을 멈추고 사람에게 결정을 넘깁니다.

    🧩 변형들 (요즘 패턴)

    • 지수 백오프(exponential backoff) — 재시도 간격을 2초, 4초, 8초처럼 배로 늘리는 방식. 서버가 이미 힘든 상황에서 전체 클라이언트가 1초마다 두드리면 장애가 더 커지기 때문.
    • 지터(jitter) — 간격에 랜덤을 조금 섞어 모든 클라이언트가 같은 순간에 재시도하는 "떼몰림"을 흩는다. 예: 2초 × (0.8~1.2).
    • "조용한 재시도" 금지 — 뒤에서 몰래 재시도하면 사용자는 그냥 멈춘 줄 알고 새로고침·중복 결제를 한다. 시도 횟수와 남은 시간을 보여주는 쪽이 안전하다.
    • 중단권 제공 — 카운트다운 중 "지금 재시도"와 "취소"를 함께. 기다림을 강요하지 않는다.
    • 최종 실패 화면 — 재시도 버튼 + 대안(다른 결제수단, 고객센터) + 참조 코드. 오류 코드가 있어야 문의가 처리된다.

    💻 코드 (복붙용)

    // 지수 백오프 + 지터, 그리고 UI에 남은 시간을 노출
const MAX = 3;
function delayFor(attempt) {            // attempt: 1,2,3...
  const base = 2000 * 2 ** (attempt - 1);      // 2s, 4s, 8s
  return Math.round(base * (0.8 + Math.random() * 0.4)); // ±20% 지터
}

async function requestWithRetry(run, onWait) {
  for (let attempt = 1; attempt <= MAX; attempt++) {
    try { return await run(); }
    catch (err) {
      if (!isRetryable(err) || attempt === MAX) throw err;
      await onWait(attempt, delayFor(attempt)); // ← 카운트다운을 화면에 그린다
    }
  }
}

// 재시도해도 되는 오류만 재시도 (중요)
const isRetryable = e =>
  e.status === 429 || e.status >= 500 || e.name === "NetworkError";

    ♿ 접근성·상태 설계

    • 상태 영역에 role="status" + aria-live="polite". 실패·성공·대기 전환이 스크린리더에 자동으로 읽힌다. 매초 바뀌는 카운트다운 숫자는 aria-hidden으로 빼서 1초마다 낭독되는 사고를 막는다.
    • 상태를 색으로만 구분하지 않는다. 아이콘·문구를 함께 둬야 색각 이상 사용자도 구분한다.
    • 회전 스피너는 prefers-reduced-motion에서 아주 느리게(또는 정지 + 텍스트로 대체).
    • 요청 중에는 실행 버튼을 disabled로. 결제는 중복 제출이 곧 금전 사고다. 서버 쪽 멱등키(idempotency key)가 최종 방어선. 멱등키: 같은 키로 온 요청은 몇 번을 받아도 한 번만 처리하게 만드는 식별자.

    🧠 paysable 적용 포인트

    결제 승인 API는 타임아웃·5xx가 실제로 발생하고, 그때 "실패"로 단정하면 승인은 됐는데 화면은 실패인 최악의 상태가 된다. 그래서 (1) 재시도 가능한 오류만 재시도하고(4xx 중 카드 거절 같은 건 재시도 금지), (2) 모든 재시도에 동일한 멱등키를 실어 중복 승인을 막고, (3) 최종 실패 화면엔 승인 조회로 이어지는 참조 코드를 반드시 노출한다. UI 쪽 재시도는 어디까지나 서버 멱등성이 보장될 때만 안전하다.

    🌀 interpolate-size와 calc-size() 트렌드·개념

    "아코디언을 부드럽게 펼치기"는 CSS에서 오래 안 되던 일이다. height: 0 → auto는 애니메이션이 안 걸려서, 다들 max-height: 500px 같은 대충 큰 값을 넣거나 JS로 높이를 실측해왔다. interpolate-size: allow-keywords 한 줄이면 auto·min-content 같은 키워드 크기까지 전환 대상이 된다.

    ✅ 새 방식 — height: 0 → auto

    두 줄짜리 짧은 설명.
    내용이 얼마나 길든 상관없습니다. 실제 높이를 브라우저가 계산해서 그만큼만 부드럽게 펼칩니다. 여기에 문단이 더 붙어도, 이미지가 들어와도 코드를 고칠 필요가 없습니다. 이게 핵심입니다.

    높이를 미리 알 필요가 없다. 내용이 늘어도 코드 수정 없음.

    ⚠️ 옛 방식 — max-height: 70px 추측

    두 줄짜리 짧은 설명.
    내용이 얼마나 길든 상관없습니다. 실제 높이를 브라우저가 계산해서 그만큼만 부드럽게 펼칩니다. 여기에 문단이 더 붙어도, 이미지가 들어와도 코드를 고칠 필요가 없습니다. 이게 핵심입니다.

    추측값이 작으면 내용이 잘리고, 크면 짧은 항목이 늦게 열리는 것처럼 보인다(빈 공간을 지나가느라).

    🧮 calc-size(auto, size + 16px) — 실제 높이에 계산 얹기

    auto가 계산한 진짜 높이에 여백 16px을 더한 값으로 전환합니다. calc-size()를 쓰면 interpolate-size는 따로 안 켜도 자동 적용됩니다.

    키워드 크기를 수식에 넣을 수 있는 유일한 방법. calc(auto + 16px)은 안 되고 calc-size(auto, size + 16px)만 된다(size가 auto의 실제 값).

    지원 여부 확인 중…

    📈 왜 지금 뜨나 / 어디에 쓰나

    • JS 높이 실측 코드를 지운다 — 아코디언·<details>·알림 배너·1번 섹션의 모달 위저드 높이 전환까지, "높이를 재서 px로 넣는" 보일러플레이트가 통째로 사라진다.
    • 점진적 향상(progressive enhancement)에 완벽히 맞는다 — 미지원 브라우저는 전환 없이 그냥 0에서 auto로 툭 바뀔 뿐, 깨지지 않는다. 폴백을 따로 짤 필요가 없다. 점진적 향상: 기본 동작은 어디서나 되게 하고, 지원되는 곳에서만 더 좋은 경험을 얹는 방식.
    • 어디에 쓰나 — 결제 요약 접기/펼치기, 주문 상세 아코디언, 인라인 에러 메시지 등장, 필터 패널 확장.

    💻 코드 (복붙용)

    /* 1) 전역으로 한 번 켜두는 게 요즘 CSS 리셋의 관례 */
:root { interpolate-size: allow-keywords; }

/* 2) 그러면 이게 그냥 된다 */
.panel {
  height: 0;
  overflow: hidden;
  transition: height .3s ease;
}
.panel[data-open="true"] { height: auto; }

/* 3) 키워드 크기에 계산을 얹고 싶으면 calc-size()
      (calc-size를 쓰면 interpolate-size는 자동 적용) */
.panel-b { transition: height .3s; height: 0; }
.panel-b.open { height: calc-size(auto, size + 16px); }

/* 주의: 한쪽 끝은 반드시 길이값이어야 한다.
   auto ↔ min-content 처럼 키워드끼리는 전환되지 않는다. */

/* 지원 여부로 분기하고 싶다면 */
@supports (interpolate-size: allow-keywords) { /* ... */ }

    ♿ 접근성·상태 설계

    • 접힌 영역은 overflow:hidden만으로 포커스 가능한 요소가 숨겨지지 않는다. 안쪽에 링크·버튼이 있으면 Tab으로 들어가 보이지 않는 곳에 포커스가 갇힌다. 닫힘 상태에서 hidden="until-found"나 inert를 함께 쓰는 게 안전하다. inert: 그 안의 모든 요소를 클릭·포커스·낭독 대상에서 통째로 빼는 속성.
    • 토글 버튼에 aria-expanded와 aria-controls. 순수 CSS로 만들 수 있어도 상태 전달은 결국 속성이 한다.
    • 전환은 prefers-reduced-motion에서 끈다.

    🧠 paysable 적용 포인트

    체크아웃의 "주문 상세 펼치기", 정산 화면의 행 확장처럼 내용 길이를 미리 알 수 없는 영역이 딱 이 문법의 대상이다. 다만 2026-08 기준 Chrome·Edge 계열만 지원(그 외는 미지원, Safari·Firefox 상태는 재확인 필요 — 추정)이므로, "전환이 안 되면 그냥 즉시 열림"이라는 폴백을 전제로만 쓴다. 애니메이션이 UX의 필수 조건인 곳(예: 잔액 부족 안내처럼 시선을 끌어야 하는 곳)이라면 아직 JS 실측이나 grid-template-rows: 0fr → 1fr 기법을 병행하는 게 안전하다.

    ⚠️ 브라우저 지원 — 검색 결과 기준 Chrome·Edge만 지원이며 Safari·Firefox는 미지원으로 보인다(2026-08 시점, 최신 상태는 caniuse에서 재확인 필요 — 추정).
