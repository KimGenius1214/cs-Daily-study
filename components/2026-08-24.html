🔘 스티키 하단 CTA와 FAB 축소 · safe-area · 이중 제출 방지

모바일 결제 화면에서 가장 중요한 버튼은 대개 화면 맨 아래 고정된 CTA입니다(CTA = Call To Action, 그 화면에서 사용자가 해야 할 단 하나의 주 동작). 요즘 패턴의 핵심은 세 가지 — ① 스크롤해도 항상 보이되 내용을 가리지 않게 여백을 확보하고, ② 스크롤 방향에 따라 축소해 화면을 돌려주고, ③ 누른 뒤에는 즉시 잠가 이중 결제를 막는 것입니다.

A. 기본 스티키 바 금액 요약 + 단일 CTA

바 자체가 position:sticky; bottom:0. 아래 패딩에 env(safe-area-inset-bottom)를 더해 아이폰 홈 인디케이터에 버튼이 물리지 않게 합니다. 버튼 높이는 최소 48px.

C. FAB(플로팅 버튼) 보조 동작용

거래 내역스크롤 시 축소 ↓
스타벅스 강남-6,300원
정산 입금+1,204,000원

FAB은 주 동작이 아니라 보조 동작(추가·작성)에 씁니다. 축소돼도 아이콘만 남을 뿐 aria-label은 그대로라 스크린 리더는 계속 "거래 추가"로 읽습니다.

A·B의 결제 버튼을 눌러 보세요. 연속으로 빠르게 눌러도 요청은 한 번만 나갑니다.

💻 핵심 코드

/* 1) 바닥에 붙되 홈 인디케이터를 피한다 */
.cta-bar{
  position: sticky; bottom: 0;
  padding: 12px 14px calc(12px + env(safe-area-inset-bottom, 0px));
  background: var(--surface);
  border-top: 1px solid var(--border);
}
/* 2) 스크롤 컨테이너 맨 아래에 바 높이만큼 여백 — 마지막 항목이 가려지지 않게 */
.scroller{ padding-bottom: calc(var(--cta-h) + env(safe-area-inset-bottom, 0px)); }

/* 3) 가상 키보드가 올라와도 바가 같이 올라오도록(문서 <head>) */
<meta name="viewport"
      content="width=device-width, initial-scale=1, interactive-widget=resizes-content">
// 4) 이중 제출 방지 — disabled 대신 aria-disabled + 가드 플래그
let inFlight = false;
btn.addEventListener("click", async () => {
  if (inFlight) return;                 // 두 번째 클릭부터는 그냥 무시
  inFlight = true;
  btn.setAttribute("aria-disabled", "true");
  btn.textContent = "결제 중…";
  try {
    await pay({ idempotencyKey });      // 서버에도 멱등 키를 함께 보낸다
    btn.textContent = "결제 완료";
  } finally {
    inFlight = false;
    btn.removeAttribute("aria-disabled");
  }
});
왜 disabled가 아니라 aria-disabled인가 — disabled를 걸면 버튼이 포커스를 잃어버려서, 키보드·스크린 리더 사용자는 "내가 방금 누른 게 어디 갔지" 상태가 됩니다. aria-disabled="true"는 포커스를 유지한 채 "지금은 못 누른다"만 알려주고, 실제 차단은 JS 가드가 합니다. 멱등 키(idempotency key, 같은 요청이 두 번 도착해도 결제를 한 번만 만들게 하는 고유 값)는 UI와 별개로 서버에서 한 번 더 막아 주는 안전망입니다.

🌡️ 사실 확인

  • interactive-widget=resizes-content는 가상 키보드가 뜰 때 레이아웃 뷰포트까지 줄여, 스티키 바가 키보드 위에 남게 합니다. 브라우저별 지원 편차가 있어 필수가 아닌 개선으로 넣는 게 안전합니다.
  • env(keyboard-inset-height)로 키보드 높이만큼 띄우는 방법도 있으나, navigator.virtualKeyboard.overlaysContent = true 옵트인이 필요하고 지원 범위가 좁습니다(추정 — 프로젝트 타깃 브라우저에서 직접 확인 필요).

⌨️ 파일 업로드 드롭존 드래그앤드롭 · 진행률 · 재시도

사업자등록증·정산 증빙처럼 파일을 받는 화면은 "업로드 버튼 하나"로 끝나지 않습니다. 요즘 드롭존의 기준선은 드래그앤드롭과 클릭·키보드가 모두 되는 하나의 컨트롤, 파일별 진행률, 그리고 실패한 파일만 골라 다시 올리는 재시도입니다. 아래는 서버 없이 업로드를 흉내 낸 것이라 일부러 가끔 실패합니다.

0 / 0 완료

    아직 선택된 파일이 없습니다. 데모용 샘플을 넣어 보려면

    키보드로도 써 보세요 — Tab으로 드롭존에 가서 Enter, 목록 안의 재시도·삭제 버튼도 전부 탭 순서에 들어 있습니다.

    💻 핵심 코드

    // 1) 드롭존은 <button>으로 만들고, 진짜 <input type="file">은 시각적으로만 숨긴다
//    (display:none 이면 일부 보조기술이 못 찾으므로 sr-only 클래스를 쓴다)
zone.addEventListener("click", () => input.click());
input.addEventListener("change", e => addFiles(e.target.files));

// 2) 드래그 상태는 카운터로 관리 — 자식 위를 지날 때 dragleave가 튀는 걸 막는다
let depth = 0;
["dragenter","dragover"].forEach(t => zone.addEventListener(t, e => {
  e.preventDefault();                    // 이걸 안 하면 브라우저가 파일을 열어버린다
  if (t === "dragenter") depth++;
  zone.classList.add("over");
}));
zone.addEventListener("dragleave", () => { if (--depth <= 0) zone.classList.remove("over"); });
zone.addEventListener("drop", e => {
  e.preventDefault(); depth = 0; zone.classList.remove("over");
  addFiles(e.dataTransfer.files);
});
    // 3) 진행률은 fetch가 아니라 XMLHttpRequest.upload.onprogress 로 받는다
//    (fetch의 요청 본문 진행률은 아직 표준 지원이 넓지 않다)
function upload(item){
  const xhr = new XMLHttpRequest();
  item.xhr = xhr;                                   // 취소용으로 들고 있는다
  xhr.upload.onprogress = e => {
    if (e.lengthComputable) setProgress(item, e.loaded / e.total);
  };
  xhr.onload  = () => xhr.status < 400 ? markDone(item) : markError(item);
  xhr.onerror = () => markError(item);              // 실패해도 목록에서 지우지 않는다
  xhr.open("POST", "/upload");
  const fd = new FormData(); fd.append("file", item.file);
  xhr.send(fd);
}
// 취소는 xhr.abort(), 재시도는 같은 item으로 upload(item) 재호출

    ♿ 접근성·상태 설계

    • 드래그는 반드시 대체 경로가 있어야 합니다. 드래그앤드롭만 되는 업로드는 키보드·터치 사용자를 배제합니다 — 클릭/Enter로 파일 선택창이 열리는 게 기본이고, 드래그는 편의 기능입니다.
    • 진행률은 <progress>나 role="progressbar" + aria-valuenow로 값을 노출합니다. 다만 1%마다 읽어 주면 시끄러우니, 완료·실패 같은 상태 변화만 aria-live="polite" 영역에 씁니다.
    • 실패한 파일은 목록에서 지우지 않습니다. 지우면 사용자가 뭘 다시 골라야 하는지 모릅니다. 자리에 남기고 이유(용량 초과·네트워크 오류)와 재시도 버튼을 붙입니다.
    • 검증은 선택 즉시(용량·확장자) 합니다. 다 올린 뒤에 "이 파일은 안 됩니다"라고 하면 시간과 데이터가 낭비됩니다.
    • accept 속성은 파일 선택창의 기본 필터일 뿐 보증이 아닙니다. 클라이언트 검증과 서버 검증을 둘 다 둡니다.

    🌀 브랜드 색 하나로 상태 색 파생 color-mix() · relative color

    예전에는 버튼 하나를 위해 기본·호버·클릭·연한배경·테두리·비활성 색을 손으로 여섯 개 정해 변수에 박았습니다. 요즘은 브랜드 색 하나만 정하고 나머지는 CSS가 계산합니다. 아래에서 색을 바꿔 보면 파생 토큰과 버튼이 전부 따라옵니다.

    프리셋:
    --brand
    --b-hover
    --b-active
    --b-soft
    --b-border
    --b-muted
    --b-deep
    승인 대기

    호버·클릭·포커스 링까지 전부 브랜드 색에서 계산된 값입니다. 다크 모드로 토글하면 같은 공식이 흰색 쪽으로 섞여 어두운 배경에서도 대비가 유지됩니다.

    지원 여부 확인 중…

    📈 왜 지금 뜨나 / 어디에 쓰나

    • color-mix()는 두 색을 정해진 비율로 섞는 CSS 함수입니다. color-mix(in oklab, var(--brand) 86%, #000) = "브랜드색 86% + 검정 14%" → 자연스러운 호버 색.
    • relative color syntax(상대 색 문법)는 기존 색을 분해해 일부만 바꾸는 문법입니다. oklch(from var(--brand) l calc(c * 0.28) h) = "밝기와 색상은 그대로, 채도만 28%로" → 비활성 버튼 색이 브랜드 계열을 유지한 채 차분해집니다.
    • in oklab/oklch를 쓰는 이유: sRGB에서 섞으면 중간색이 탁하게 죽는 구간이 있는데, OKLab 계열은 사람 눈이 느끼는 밝기에 맞춰 설계돼 섞은 결과가 예측 가능합니다.
    • 실무 효과: 화이트라벨(고객사마다 브랜드 색이 다른 결제 페이지)에서 변수 하나만 주입하면 전체 팔레트가 따라옵니다. 테마마다 색 40개를 관리할 필요가 없습니다.
    • 브라우저 지원: color-mix()는 2023년부터, 상대 색 문법은 그보다 늦게 주요 엔진에 들어왔습니다. 2026년 기준 주요 브라우저에 모두 있으나, 구형 지원이 필요하면 @supports로 폴백 값을 함께 두세요.

    💻 코드 (복붙용)

    :root{
  --brand: #4f46e5;                                          /* 정하는 건 이거 하나 */

  --brand-hover : color-mix(in oklab, var(--brand) 86%, #000);
  --brand-active: color-mix(in oklab, var(--brand) 72%, #000);
  --brand-soft  : color-mix(in oklab, var(--brand) 12%, #fff);
  --brand-border: color-mix(in oklab, var(--brand) 32%, #fff);
  --brand-ring  : color-mix(in srgb,  var(--brand) 55%, transparent);
  --brand-muted : oklch(from var(--brand) l calc(c * .28) h); /* 채도만 낮춤 */
  --brand-deep  : oklch(from var(--brand) .42 c h);           /* 밝은 배경 위 글자용 */
}
@media (prefers-color-scheme: dark){
  :root{                                   /* 다크에선 검정 대신 흰색 쪽으로 */
    --brand-hover : color-mix(in oklab, var(--brand) 84%, #fff);
    --brand-active: color-mix(in oklab, var(--brand) 70%, #fff);
    --brand-soft  : color-mix(in oklab, var(--brand) 22%, #0b0e13);
    --brand-deep  : oklch(from var(--brand) .82 c h);
  }
}
/* 구형 폴백 */
@supports not (color: color-mix(in oklab, red, blue)){
  :root{ --brand-hover:#4338ca; --brand-active:#3730a3; --brand-soft:#eef0fe; }
}
    주의 — 색을 계산으로 만든다고 대비(contrast)까지 자동으로 안전해지는 건 아닙니다. 밝은 브랜드 색(예: 앰버) 위에 흰 글씨를 얹으면 WCAG 대비 기준(본문 4.5:1, 큰 글씨 3:1)에 미달할 수 있습니다. 위 데모에서 앰버를 골라 보면 실제로 아슬아슬합니다. 전경색은 파생값에 맡기지 말고 밝기 기준으로 흑/백을 골라 검증하세요.
