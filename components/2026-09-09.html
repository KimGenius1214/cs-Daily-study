💳 3D Secure 인증 흐름 결제·체크아웃 UX

카드 결제 중간에 은행이 "본인 맞아요?"를 묻는 단계를 3D Secure(3DS)라고 합니다. 화면을 통째로 은행 사이트로 넘길지, 우리 페이지 위에 창을 띄울지, 아예 안 묻고 넘어갈지에 따라 이탈률과 실패 복구 경험이 완전히 달라집니다.

한 줄 용어

  • 프릭션리스(frictionless) — 카드사가 위험이 낮다고 판단해 사용자에게 아무것도 묻지 않고 통과시키는 경우.
  • 챌린지(challenge) — 카드사가 추가 확인(문자 인증번호, 앱 승인 등)을 요구하는 경우.
  • 멱등키(idempotency key) — 같은 요청이 두 번 가도 결제는 한 번만 되도록, 요청마다 붙이는 고유 문자열.
  • aria-busy — "이 영역은 지금 처리 중"이라고 보조기기에 알리는 HTML 속성.

🏦 우리은행 안심클릭

지금 브라우저가 은행 페이지로 넘어간 상태입니다. 우리 앱의 자바스크립트 메모리는 여기서 전부 날아갑니다.

그래서 리다이렉트 방식은 결제 세션 id와 멱등키를 sessionStorage(또는 서버 세션)에 미리 저장해 두고, 돌아온 뒤 "결제 확인 중" 화면에서 서버에 결과를 물어보는 폴링 단계가 반드시 필요합니다.

💡 모달 방식은 뒤에 주문 요약이 계속 보여 "내가 뭘 사는 중이었는지"를 잃지 않습니다. 리다이렉트는 그 맥락이 통째로 사라지므로, 돌아왔을 때 같은 금액·같은 카드가 그대로 보이도록 복구해 줘야 합니다.

🧩 변형 셋을 뭐로 고르나

방식언제주의점
인라인 모달/iframeSPA·자체 체크아웃 화면. 기본값으로 권장 결과를 postMessage로 받는 동안 부모에 aria-busy="true". 딤 처리가 은행 창의 닫기 버튼을 가리면 안 됨
전체 리다이렉트모달을 못 띄우는 환경, 일부 은행이 iframe을 거부할 때 폴백 복귀 URL에 결제 세션 id. 새로고침·뒤로가기로 이중 결제되지 않게 멱등키 고정
프릭션리스카드사가 추가 확인을 요구하지 않은 경우 너무 빨라서 사용자가 인증이 있었는지도 모름 → 짧은 "확인됨" 상태를 의도적으로 보여줌

업계 문서들은 대체로 모달/iframe을 기본값으로, 리다이렉트를 폴백으로 권합니다(Stripe·Ixopay 등). "리다이렉트가 모바일에서 이탈이 몇 배 더 크다"는 식의 구체적 수치는 출처마다 달라 여기서는 단정하지 않습니다(추정).

💻 코드 (복붙용) — 중복 결제를 막는 제출 잠금

// 결제 시작 시 멱등키를 "한 번만" 만들어 세션에 저장한다.
// 리다이렉트로 페이지가 통째로 새로 뜨거나, 사용자가 새로고침해도 같은 키가 재사용된다.
function getIdempotencyKey(orderId) {
  const k = `pay:${orderId}:idem`;
  let v = sessionStorage.getItem(k);
  if (!v) { v = crypto.randomUUID(); sessionStorage.setItem(k, v); }
  return v;
}

async function pay(orderId) {
  const box = document.getElementById('coBox');
  box.setAttribute('aria-busy', 'true');       // 보조기기: 지금 처리 중
  payBtn.disabled = true;                       // 더블클릭 방지 (UI 레벨)

  const res = await fetch('/api/payments', {
    method: 'POST',
    headers: { 'Idempotency-Key': getIdempotencyKey(orderId) }, // 서버 레벨 방어
    body: JSON.stringify({ orderId }),
  }).then(r => r.json());

  if (res.status === 'requires_action') {
    openChallengeModal(res.challengeUrl);       // 모달 우선
  } else {
    finish(res);
  }
}

// 리다이렉트에서 돌아왔을 때: 결제 세션이 남아 있으면 곧장 확인 화면으로
window.addEventListener('DOMContentLoaded', () => {
  const pending = sessionStorage.getItem('pay:pendingId');
  if (pending) pollPaymentResult(pending);      // "결제 확인 중…" 상태부터 시작
});

♿ 접근성·상태 설계

  • 인증 대기 중에는 결제 영역에 aria-busy="true". 이게 없으면 스크린리더 사용자에겐 "화면이 그냥 멈춘 것"으로 들립니다.
  • 상태 메시지는 role="status" aria-live="polite" 영역에. 모달을 <dialog>.showModal()로 열면 포커스 트랩과 Esc는 브라우저가 처리합니다.
  • 모달을 닫으면 포커스는 결제 버튼으로 되돌립니다. "인증이 취소됐어요, 다시 시도할까요?"까지 같이 안내.
  • 실패했을 때 장바구니로 되돌리지 않습니다. 같은 화면에서 재시도 또는 다른 결제수단 선택을 제안합니다.
  • 스피너 회전은 prefers-reduced-motion(모션 줄이기 설정)에서 느리게 — 완전히 없애면 진행 중인지 알 수 없으므로 감속만.

🧠 paysable 적용 포인트

  • 결제 상태를 idle → submitting → requires_action → verifying → succeeded | failed로 명시적 상태 머신으로 두면, "버튼이 두 번 눌렸다" 류 버그가 구조적으로 사라집니다.
  • 멱등키는 주문 단위로 고정하고 재시도해도 유지. UI 잠금은 보조 수단일 뿐, 진짜 방어선은 서버 헤더입니다.
  • 인증 창을 띄우는 순간부터 서버 결과를 받을 때까지 새로고침·뒤로가기가 언제든 일어난다고 가정하고, 복구 경로를 먼저 그린 뒤 UI를 붙이는 편이 안전합니다.

⌨️ 형식 있는 번호 입력 입력·폼

사업자등록번호, 계좌번호처럼 자릿수와 구분자가 정해진 값은 일반 텍스트 입력과 다르게 다뤄야 합니다. 붙여넣기로 들어오는 온갖 형태를 받아주고, 서버에 보내기 전에 로컬에서 걸러낼 수 있는 건 걸러내는 게 핵심입니다.

한 줄 용어

  • 체크섬(checksum) — 번호 자체에 들어 있는 검산용 숫자. 오타를 서버에 물어보기 전에 잡아냅니다.
  • 표시값 / 전송값 — 화면엔 220-81-62517, 서버엔 2208162517. 두 값을 분리해 둡니다.
  • :user-invalid — 사용자가 실제로 그 칸을 만지고 나간 뒤에만 빨갛게 칠하는 CSS 선택자.
숫자만 입력하면 하이픈은 자동으로 붙습니다.
붙여넣기 테스트: 사업자번호 124.81.00998 입니다 를 그대로 붙여넣어 보세요.

✔ 붙여넣은 문자열에서 숫자만 뽑아내고, 10자리가 차면 체크섬으로 즉시 판정합니다. 중간을 수정해도 커서가 끝으로 튀지 않게 하이픈 개수만큼 커서 위치를 보정합니다.

💻 코드 (복붙용) — 커서가 안 튀는 자동 하이픈

const digitsOnly = (s) => s.replace(/\D/g, '');

function formatBRN(raw) {              // 2208162517 -> 220-81-62517
  const d = digitsOnly(raw).slice(0, 10);
  if (d.length <= 3) return d;
  if (d.length <= 5) return `${d.slice(0,3)}-${d.slice(3)}`;
  return `${d.slice(0,3)}-${d.slice(3,5)}-${d.slice(5)}`;
}

input.addEventListener('input', (e) => {
  const el = e.target;
  const before = el.selectionStart;
  // 커서 앞쪽에 "숫자가 몇 개 있었는지"를 기준점으로 삼는다
  const digitsBefore = digitsOnly(el.value.slice(0, before)).length;

  el.value = formatBRN(el.value);

  // 포맷 후, 같은 개수의 숫자를 지난 지점으로 커서를 되돌린다
  let pos = 0, seen = 0;
  while (pos < el.value.length && seen < digitsBefore) {
    if (/\d/.test(el.value[pos])) seen++;
    pos++;
  }
  el.setSelectionRange(pos, pos);
});

// 체크섬 (널리 알려진 공개 알고리즘 · 최종 확인은 서버/국세청 조회로)
function isValidBRN(v) {
  const d = digitsOnly(v);
  if (d.length !== 10) return false;
  const w = [1, 3, 7, 1, 3, 7, 1, 3, 5];
  let sum = 0;
  for (let i = 0; i < 9; i++) sum += Number(d[i]) * w[i];
  sum += Math.floor((Number(d[8]) * 5) / 10);
  return (10 - (sum % 10)) % 10 === Number(d[9]);
}

♿ 접근성·상태 설계

  • inputmode="numeric"으로 모바일 숫자 키패드를 띄우되, type="number"는 쓰지 않습니다 — 앞자리 0이 사라지고 스크롤로 값이 바뀌는 사고가 납니다.
  • 에러는 입력하는 도중이 아니라 칸을 벗어난 뒤(blur) 또는 자릿수가 다 찬 뒤에 보여줍니다. 타이핑 중 빨간불은 스트레스만 줍니다.
  • 에러 문구는 aria-describedby로 입력칸과 연결하고 aria-live="polite"로 읽어줍니다. 색만으로 알리지 않습니다.
  • 붙여넣기는 input 이벤트 하나로 처리하면 paste·자동완성·IME까지 한 번에 커버됩니다.
  • 숫자는 font-variant-numeric: tabular-nums로 자릿수를 고정해 세로로 흔들리지 않게 합니다.

🧠 paysable 적용 포인트

  • 가맹점 온보딩의 사업자번호·정산계좌는 클라이언트 체크섬 → 서버 실명확인 2단으로 두면 서버 호출 횟수가 눈에 띄게 줄어듭니다.
  • 폼 상태는 표시값이 아니라 전송값(숫자만)을 단일 출처로 두고, 화면 표시는 파생값으로 계산합니다. 저장 직전에 하이픈을 벗기는 코드가 여기저기 흩어지는 걸 막습니다.
  • 등록 완료 후 마스킹 요약 카드는 "이미 등록됨"을 한눈에 알려 중복 등록 문의를 줄여줍니다.

🌀 CSS @scope — 스타일이 새지 않게, 이름 규칙 없이 트렌드·개념

@scope는 CSS 규칙이 먹히는 구역을 직접 지정하는 문법입니다. BEM 같은 클래스 이름 규칙이나 CSS-in-JS 빌드 단계 없이도 "이 카드 안에서만"을 표현할 수 있고, 무엇보다 가장 가까운 조상이 이긴다는 새로운 우선순위 규칙(근접성)을 가져옵니다.

한 줄 용어

  • 스코프 루트 — @scope (.card)의 .card. 규칙이 시작되는 지점.
  • 스코프 리밋 / 도넛 스코프 — @scope (.article) to (.widget)처럼 아래쪽 경계까지 정하는 것. 가운데가 뚫린 도넛 모양이라 이렇게 부릅니다.
  • 근접성(proximity) — 명시도가 같을 때, DOM에서 더 가까운 스코프 루트의 규칙이 이깁니다. 기존 CSS엔 없던 판정 기준입니다.

① 근접성 — 라이트 테마 안에 다크 테마 카드가 중첩된 상황입니다. 두 방식의 결과를 비교해 보세요.

❌ 자손 선택자 겉돈다

.t-light (바깥) 바깥은 라이트. 링크 색
.t-dark (안쪽) 안쪽은 다크여야 하는데 링크 색이 바깥 규칙과 싸웁니다.
.t-light (다시 안쪽) 세 겹이 되면 어느 규칙이 이길지를 소스 순서로 추적해야 합니다.

✅ @scope 가까운 쪽이 이긴다

.s-light (바깥) 바깥은 라이트. 링크 색
.s-dark (안쪽) 안쪽은 다크. 링크 색도 자동으로 따라옵니다.
.s-light (다시 안쪽) 몇 겹이 되든 가장 가까운 조상의 규칙이 적용됩니다.

② 도넛 스코프 — @scope (.article) to (.widget). 아래 버튼으로 안쪽 상자에 .widget 클래스를 붙였다 떼 보세요. 붙이는 순간 그 안의 문단만 규칙에서 빠집니다.

본문 문단입니다. .article 스코프의 규칙(파란 굵은 글씨 + ◆)이 적용됩니다.

위젯 안의 문단입니다. .widget이 붙으면 바깥 본문 스타일이 여기까지 내려오지 않습니다.

현재: 클래스 없음 — 본문 스타일이 위젯 안까지 내려옴
지원 여부 확인 중…
이 브라우저는 @scope를 아직 지원하지 않아 위 두 데모가 스타일 없이 보입니다. 실제 서비스에서는 기존 자손 선택자를 먼저 두고 @supports at-rule(@scope) 안에서만 덮어쓰는 식으로 점진적 향상(progressive enhancement)을 적용합니다.

📈 왜 지금 뜨나 / 어디에 쓰나

  • 파이어폭스 146이 지원을 추가하면서 주요 브라우저 전부에서 동작하게 됐고, Baseline "newly available"로 분류됐습니다(크롬·엣지 118+, 사파리 17.4+, 파이어폭스 146+).
  • 서드파티 위젯, 리치 텍스트 에디터 미리보기, 사용자 입력 HTML처럼 "우리 CSS가 들어가면 안 되는 구역"이 있을 때 도넛 스코프가 정확히 그 문제를 풉니다.
  • 다크 모드 섹션이 라이트 페이지 안에 섞이는 배너·카드에서 근접성이 특히 유용합니다.
  • 주의: @scope는 명시도를 올리지 않습니다. 격리 강도는 Shadow DOM보다 약하고, 상속되는 속성(글자색 등)은 여전히 넘어옵니다. "새는 걸 줄이는 도구"지 방화벽이 아닙니다.

@scope (.theme-light) { a { color: #2563eb; } }
@scope (.theme-dark)  { a { color: #fbbf24; } }

/* 4) 점진적 향상 — 미지원 브라우저에 기본 스타일을 남겨둔다 */
.article p { color: inherit; }
@supports at-rule(@scope) {
  @scope (.article) to (.widget) { p { color: var(--brand); } }
}

@supports at-rule(...) 자체의 브라우저 지원 범위는 문서마다 서술이 갈립니다(추정). 확실히 하려면 JS에서 'CSSScopeRule' in window로 감지해 클래스를 붙이는 방식이 안전합니다 — 이 페이지가 그렇게 하고 있습니다.

🧠 paysable 적용 포인트

  • PG사 위젯이나 외부 iframe 폴백 영역처럼 우리가 통제하지 않는 마크업 주변에 도넛 스코프를 쳐 두면, 전역 리셋 CSS가 그 안을 망가뜨리는 사고를 막을 수 있습니다.
  • 영수증·명세서처럼 라이트 고정이어야 하는 블록을 다크 페이지 안에 넣을 때 근접성이 !important 없이 문제를 해결해 줍니다.
  • 다만 팀 전체 도입은 신중히 — 디버깅 시 "왜 이 규칙이 안 먹지"의 원인이 하나 더 늘어납니다. 격리가 꼭 필요한 경계에만 쓰는 편이 낫습니다.
