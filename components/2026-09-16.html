💳 결제 거절 복구 — 사유마다 다음 행동이 달라야 한다 결제·체크아웃 UX

"결제에 실패했습니다"는 사용자에게 아무것도 알려주지 않는다. PG/카드사가 돌려주는 거절 사유 코드를 몇 개의 복구 시나리오로 묶어, 각 시나리오에 서로 다른 주 액션 하나를 주는 게 요즘 방식이다. 아래 시뮬레이터에서 사유를 바꿔가며 화면이 어떻게 달라지는지 보자.

같은 "실패"라도 재시도가 의미 있는 경우(일시적 거절)와 재시도가 무의미한 경우(만료·분실)는 주 액션이 완전히 달라야 한다. 주 액션은 화면당 하나만 강조하고, 나머지는 보조 버튼으로 내린다.

변형 B — 무한 재시도를 막는 가드

같은 카드 3회 실패 → 재시도 잠금 + 경로 전환

위 시뮬레이터에서 같은 카드로 계속 실패시켜 보세요. 3회째부터 "다시 시도"가 잠기고, 화면이 다른 결제수단 등록 쪽으로 사용자를 옮깁니다. 성공하면 카운터는 0으로 돌아갑니다.

  • 연속 실패 카운터는 카드 단위로 센다(카드를 바꾸면 리셋).
  • 잠금은 "버튼을 없애기"가 아니라 쿨다운 초읽기 + 대체 경로 제시로 한다.
  • 카드사가 이미 막은 카드를 계속 두드리면 사기 의심 플래그가 쌓일 수 있다(카드망 정책은 사별로 다름 — 추정).

✅ 복구 화면

카드 한도 또는 잔액이 부족합니다

결제는 이뤄지지 않았고 금액이 빠져나가지 않았습니다. 다른 카드로 진행하거나 잠시 후 다시 시도해 주세요.

  • 사유를 사용자 언어로 번역했다.
  • 돈이 빠져나갔는지를 먼저 안심시킨다 — 결제 실패에서 가장 큰 불안.
  • 주 액션(다른 카드) 하나 + 보조 액션 하나. 선택지를 3개 이상 주지 않는다.
거절 사유 그룹과 권장 주 액션
그룹대표 사유재시도 의미주 액션
일시적 거절잔액/한도 부족, 발급사 거절시간 두고 가능다른 카드로 결제 (보조: 다시 시도)
정보 오류CVC 불일치, 유효기간 오류고치면 즉시카드 정보 수정 (틀린 칸으로 포커스)
카드 자체 불가만료, 분실/도난, 정지무의미다른 결제수단 등록만 노출
시스템 오류처리 오류, 타임아웃즉시 1~2회다시 시도 (멱등키 유지)
멱등키(idempotency key) = 같은 요청을 여러 번 보내도 서버가 한 번만 처리하도록 붙이는 고유 식별자. 재시도 버튼을 누를 때 같은 키를 유지해야 이중 결제가 안 난다. 단, 사용자가 카드를 바꿔서 재시도하는 건 다른 결제이므로 키를 새로 발급해야 한다 — 이 구분을 놓치면 "카드 바꿨는데 예전 카드로 결제됨" 버그가 난다.

변형 B — 나쁜 구현 재현

"hidden만 씌우고 required를 남겨두면" 무슨 일이 생기나

위에서 ❌ 나쁜 구현으로 전환을 누르고 다시 제출해 보세요. 화면에 보이지도 않는 필드 때문에 제출이 막히고, 브라우저 기본 검증은 숨은 필드에 포커스를 줄 수 없어 아무 말 없이 실패합니다(콘솔에도 안 나옴). payload에도 반대편 값이 딸려 들어갑니다. 실무에서 "버튼을 눌러도 아무 반응이 없어요" 문의의 단골 원인.

♿ 여기서 놓치기 쉬운 것

  • 전환을 알리기: 화면 중간이 통째로 바뀌는데 스크린리더는 침묵한다. role="status" 영역에 "사업자 입력으로 전환됨 — 3개 항목" 한 줄을 넣는다.
  • 포커스 이동: 전환 직후 새 분기의 첫 입력으로 포커스를 옮긴다. 키보드 사용자가 Tab을 10번 누르지 않게.
  • 입력값 보존: 개인 → 사업자 → 개인으로 돌아왔을 때 아까 친 값이 살아 있어야 한다. disabled는 값을 지우지 않으므로 그대로 남는다(언마운트 방식의 장점).
  • 세그먼트는 라디오다: 시각적으로 버튼이어도 의미는 "택1". role="radiogroup" + 화살표 키 이동이 정석이며, 위 데모는 aria-pressed 토글 그룹으로 단순화했다(둘 다 실무에서 쓰인다).

🌀 ::details-content — 펼침 애니메이션에서 드디어 래퍼 div를 뺀다 트렌드·개념

<details>는 접고 펴는 걸 브라우저가 공짜로 해주지만, 부드럽게 펼치기가 오랫동안 불가능했다. 열리는 부분을 가리킬 선택자가 없어서, 다들 안쪽에 div.wrapper를 하나 더 넣고 JS로 높이를 쟀다. ::details-content는 그 "열리는 부분"을 CSS가 직접 가리키게 해준다.

목록 행 펼치기는 접근성 요구사항이 많은 컴포넌트다(확장 상태, 키보드, 포커스 순서). <details>를 쓰면 그 전부를 브라우저가 처리하고, 우리는 색과 모션만 얹는다. 

/* ① 높이 키워드(auto)로의 전환을 허용 */
:root { interpolate-size: allow-keywords; }

/* ② 열리는 부분 자체를 선택 — 래퍼 div 불필요 */
details::details-content {
  block-size: 0;
  overflow: clip;
  /* content-visibility는 값이 뚝 끊기는 속성 → allow-discrete로 전환 시점을 맞춤 */
  transition: block-size .3s ease, content-visibility .3s allow-discrete;
}
details[open]::details-content { block-size: auto; }

/* ③ 미지원 브라우저 폴백 — 애니메이션만 빠지고 기능은 그대로 */
@supports not selector(::details-content) {
  details::details-content { block-size: auto; }
}
@media (prefers-reduced-motion: reduce) {
  details::details-content { transition: none; }
}

용어 한 줄 정리

  • ::details-content — <details>에서 <summary>를 뺀 펼쳐지는 영역을 가리키는 가상 요소. 그동안 DOM에 없던 부분이라 CSS가 잡을 수 없었다.
  • interpolate-size: allow-keywords — height:auto처럼 "계산해봐야 아는 값"으로의 전환을 허용하는 스위치. 이게 없으면 0 → auto 전환은 그냥 점프한다.
  • transition-behavior: allow-discrete(위 단축 표기의 allow-discrete) — display, content-visibility처럼 중간값이 없는 속성도 전환 타이밍에 맞춰 바꿔주는 옵션.
  • 폴백(fallback) — 지원하지 않는 환경에서 자동으로 물러나는 대안. 여기선 "애니메이션 없이 즉시 열림"이라 기능 손실이 0이다. 이런 기능이 점진적 적용(progressive enhancement)에 가장 좋은 후보.
지원 현황(2026-09 기준, 검색 확인): Chrome/Edge 131+, Firefox 143+, Safari 18.4+에서 동작하며 2025년 9월 Baseline에 편입된 것으로 보고된다. 다만 팀의 실제 지원 하한(예: 사내 구형 WebView, 키오스크 브라우저)은 별도로 확인해야 한다 — 위 폴백 블록을 반드시 함께 넣을 것. 각 브라우저의 세부 동작 차이는 직접 검증하지 않았다(추정).
