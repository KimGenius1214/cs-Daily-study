💳 주문 금액 요약 패널 결제·체크아웃 UX

결제 직전 화면에서 사용자가 가장 오래 쳐다보는 건 상품 사진이 아니라 “그래서 얼마 나가는데” 숫자다. 총액은 항상 보이게 두고, 내역은 접어두고, 금액이 바뀌면 화면을 읽지 않는 사람에게도 들리게 알린다.

변형 A — 총액 고정 + 내역 접기 + 변경 알림

옵션을 켜고 꺼 보세요 — 총액과 내역, 그리고 아래 알림 로그가 함께 바뀝니다

체크박스는 <label>으로 통째로 감싸 터치 영역을 넓혔고, 선택 스타일은 :has(input:checked)로 JS 없이 입혔습니다.

결제 금액

    세부 내역 보기
      최종 결제 금액 0원

      부가세 포함 · 결제 시점에 최종 확정됩니다

      위 로그는 role="status" aria-live="polite" 영역입니다. 스크린 리더는 “금액이 바뀌었다”는 사실을 포커스를 뺏기지 않고 듣습니다. (aria-live: 화면 일부가 바뀌었을 때 보조기기에 그 변화를 읽어주게 하는 속성. polite는 지금 읽던 문장이 끝난 뒤에 끼워 읽는다는 뜻)

      왜 접었나 — 소계·할인·수수료·부가세를 전부 펼쳐 놓으면 “총액”이 다섯 개 숫자 중 하나가 되어 버립니다. 총액만 크게 남기고 나머지는 <details>로 접으면, 확인하고 싶은 사람은 열어 보고 대부분은 총액만 보고 넘어갑니다. 단 주의 수수료·배송비처럼 “내가 모르고 냈다”가 될 수 있는 항목은 접지 말고 항상 노출하세요. 접는 건 계산 과정이지 추가 부담이 아닙니다.

      변형 B — 확정 금액 vs 추정 금액 (통화·환율)

      통화를 바꿔 보세요 — 원화 환산은 “확정”이 아니라 “추정”으로 보여야 합니다

      결제 금액

      • 상품 금액128,000원
      • 상품 할인-8,000원
      최종 결제 금액 120,000원
      ≈ 약 165,600원 (1 USD = 1,380원 기준)
      실제 청구 금액은 카드사 승인 시점 환율·해외 수수료에 따라 달라질 수 있습니다.

      규칙 하나만 지키면 됩니다. 확정 금액은 굵게·크게, 추정 금액은 ≈ / 약을 붙여 작게. 같은 크기로 나란히 두면 사용자는 둘 다 확정으로 읽고, 나중에 청구서가 다르면 그게 CS 티켓이 됩니다.

      변형 C — 모바일: 하단 고정 요약 바

      모바일에선 요약 패널이 스크롤 밖으로 사라집니다 — 총액만 하단에 붙이고 펼치게
      주문서
      • 상품 금액128,000원
      • 상품 할인-8,000원
      • 배송비0원
      120,000원
      • 하단 바는 position:fixed + padding-bottom:env(safe-area-inset-bottom)로 아이폰 홈 인디케이터를 피합니다.
      • 펼침 버튼은 aria-expanded와 aria-controls를 붙여야 스크린 리더가 “접힘/펼침”을 읽습니다.
      • 본문 하단에 바 높이만큼 padding-bottom을 줘야 마지막 항목이 바에 가려지지 않습니다. (아주 흔한 버그)
      • 결제 버튼은 바 안에 있어야 합니다. 총액과 버튼이 떨어져 있으면 “내가 지금 누르는 금액”이 흔들립니다.

      💻 복붙용 — 금액 변경 알림

      <!-- 총액은 시각적으로만 갱신하고, 변화 사실은 live 영역이 따로 말한다 -->
<p class="total"><span aria-hidden="true">최종 결제 금액</span>
  <strong id="total">120,000원</strong></p>
<p id="totalLive" role="status" aria-live="polite" aria-atomic="true" class="sr-only"></p>

<script>
function setTotal(next, reason) {
  document.getElementById('total').textContent = format(next);
  // 금액 자체를 aria-live로 두면 타이핑 중에도 계속 읽어 시끄럽다.
  // '무엇 때문에 얼마가 됐는지' 한 문장으로 요약해서 따로 알린다.
  document.getElementById('totalLive').textContent =
    reason + ' 적용. 최종 결제 금액 ' + format(next) + '.';
}
</script>

      ♿ 접근성·상태 설계

      • 금액 노드에 직접 aria-live를 걸지 않는다. 수량 스테퍼를 연타하면 중간값이 전부 읽혀 소음이 됩니다. 변경 이유 + 최종 금액을 한 문장으로 만들어 별도 role="status"에 넣으세요.
      • 숫자는 font-variant-numeric: tabular-nums. 금액이 바뀔 때 자릿수가 들썩이지 않습니다.
      • 0원 항목 처리 — “배송비 0원”은 남기고(무료라는 정보), “쿠폰 0원”은 숨깁니다(선택 안 한 항목). 기준: 사용자에게 이득인 0은 보여주고, 비어 있는 0은 지운다.
      • 로딩 중 총액은 —나 스켈레톤으로 두고, 이전 금액을 그대로 두지 마세요. 옛 금액이 남아 있으면 그게 최종가인 줄 알고 결제합니다.
      • prefers-reduced-motion(사용자가 OS에서 “동작 줄이기”를 켠 상태)일 때 총액 강조 애니메이션은 끕니다. 위 데모의 살짝 커지는 효과도 그때는 실행되지 않습니다.

      🧠 paysable 적용 포인트

      • 결제 요약은 서버 계산 값만 렌더하는 게 안전합니다. 프론트에서 할인·수수료를 다시 계산하면 반올림 규칙 하나 어긋나도 “화면 금액 ≠ 승인 금액”이 되고, 그건 곧 클레임입니다. 프론트는 {label, amount, sign} 배열을 받아 그리기만.
      • 총액 갱신은 디바운스(연속 입력이 멈춘 뒤 한 번만 실행) 후 재견적 API 1회 호출로 묶고, 응답이 늦게 도착한 오래된 요청은 버립니다(요청마다 시퀀스 번호를 달고 최신 것만 반영).
      • 재견적 실패 시 결제 버튼을 잠그세요. 금액을 모른 채 결제 요청이 나가는 게 최악입니다.

      ⌨️ 폼 자동 임시저장 입력·폼

      긴 폼에서 사용자가 가장 화나는 순간은 검증 실패가 아니라 “다 썼는데 날아갔다”입니다. 자동 저장은 기능 하나가 아니라 저장 상태 · 복구 제안 · 이탈 경고 세 개가 붙어야 완성됩니다.

      변형 A — 저장 상태 표시 (idle → dirty → saving → saved / error)

      타이핑해 보세요 — 멈추고 0.8초 뒤 저장됩니다. “다음 저장 실패”를 켜면 실패 복구 흐름을 볼 수 있습니다
      작성하던 내용이 남아 있습니다 2분 전 자동 저장 · 제목 외 2개 항목
      아직 변경 사항 없음

      “새로고침 시뮬레이션”을 누르면 폼이 비워지고 복구 제안 배너가 뜹니다. 이게 자동 저장의 본체입니다 — 저장만 하고 복구 동선이 없으면 사용자는 저장된 줄도 모릅니다.

      변형 B — 이탈 경고는 “진짜 안 저장됐을 때만”

      더티 상태(저장 안 된 변경)에서만 경고를 켭니다
      현재: 경고 꺼짐 — 저장되지 않은 변경이 없으므로 beforeunload 핸들러를 등록하지 않은 상태입니다. 위 폼에 뭔가 입력하면 여기가 바뀝니다.

      흔한 안티패턴: 폼에 들어오자마자 beforeunload를 무조건 등록해 두는 것. 아무것도 안 고치고 나가려는 사람까지 “변경 사항이 저장되지 않을 수 있습니다” 창을 만나고, 그게 반복되면 사용자는 경고 자체를 안 읽게 됩니다. 더티일 때만 등록하고, 저장 성공 시 즉시 해제하세요.

      브라우저는 beforeunload의 커스텀 메시지를 더 이상 보여주지 않습니다(브라우저 기본 문구로 대체). 즉 “무엇이 사라지는지”는 그 창으로 설명할 수 없습니다. 설명은 화면 안 저장 상태 표시가 맡아야 합니다.

      💻 복붙용 — 디바운스 자동 저장 훅 (React/TS)

      // debounce: 입력이 멈춘 뒤 일정 시간이 지나야 한 번만 실행하는 기법.
// 글자마다 저장 요청을 보내지 않기 위해 씁니다.
type SaveState = 'idle' | 'dirty' | 'saving' | 'saved' | 'error';

export function useAutosave<T>(value: T, save: (v: T) => Promise<void>, delay = 800) {
  const [state, setState] = useState<SaveState>('idle');
  const first = useRef(true);
  const seq = useRef(0);               // 늦게 도착한 옛 응답을 버리기 위한 순번

  useEffect(() => {
    if (first.current) { first.current = false; return; }  // 마운트 직후는 저장하지 않는다
    setState('dirty');
    const id = setTimeout(async () => {
      const my = ++seq.current;
      setState('saving');
      try {
        await save(value);
        if (my === seq.current) setState('saved');
      } catch {
        if (my === seq.current) setState('error');         // 실패해도 입력값은 그대로 둔다
      }
    }, delay);
    return () => clearTimeout(id);
  }, [value, delay, save]);

  // 저장 안 된 변경이 있을 때만 이탈 경고를 건다
  useEffect(() => {
    if (state !== 'dirty' && state !== 'error') return;
    const h = (e: BeforeUnloadEvent) => { e.preventDefault(); };
    window.addEventListener('beforeunload', h);
    return () => window.removeEventListener('beforeunload', h);
  }, [state]);

  return state;
}

      ♿ 접근성·상태 설계

      • 저장 상태는 role="status" + aria-live="polite". “저장 중”이 계속 읽히면 시끄러우니, 상태가 바뀔 때만 텍스트를 교체하세요.
      • 색만으로 구분하지 않기 — 초록 점 하나로 “저장됨”을 표현하면 색각 이상 사용자에게 전달되지 않습니다. 점 + 텍스트를 함께 둡니다.
      • 실패는 조용히 넘기지 않기. 실패 상태에선 명시적인 “다시 저장” 버튼을 띄우고, 자동 재시도는 지수 백오프(재시도 간격을 1초→2초→4초로 늘리는 방식)로 1~2회만.
      • 복구 배너의 두 버튼은 대등하게. “이어서 작성 / 새로 작성” 중 하나를 흐리게 만들면 실수로 초안을 날립니다. 파괴적인 쪽(새로 작성)은 한 번 더 확인하거나 되돌리기를 제공하세요.
      • 자동 저장 중에 포커스를 옮기거나 커서를 재배치하면 안 됩니다. 저장은 백그라운드 작업입니다.

      🧠 paysable 적용 포인트

      • 결제 정보는 자동 저장 대상이 아닙니다. 카드번호·CVC·비밀번호는 로컬 스토리지에도, 서버 초안에도 남기지 않습니다. 자동 저장은 정산 문의, 가맹점 등록 신청, 세금계산서 요청처럼 길고 민감하지 않은 폼에만.
      • 초안 저장 API는 제출 API와 분리하고, 초안에는 검증을 걸지 않습니다. 반쯤 쓴 이메일에 “형식이 올바르지 않습니다”가 뜨면 자동 저장이 방해가 됩니다.
      • 여러 탭에서 같은 폼을 열었을 때가 진짜 함정입니다. 초안에 버전(또는 updatedAt)을 실어 보내고, 서버가 더 최신이면 덮어쓰지 말고 “다른 곳에서 수정됨” 배너를 띄우세요.

      🌀 text-box-trim — 글자 위아래 ‘보이지 않는 여백’을 CSS가 잘라낸다 트렌드·개념

      버튼 안 글자가 미묘하게 위로 붙어 보여서 padding-top: 9px; padding-bottom: 11px 같은 홀수 보정을 해본 적 있다면, 그건 여러분 눈이 이상한 게 아니라 폰트가 글자 위아래에 들고 다니는 여백(half-leading) 때문입니다. text-box-trim은 그 여백을 CSS가 직접 잘라내게 하는 속성입니다.

      지원 여부 확인 중…

      📈 왜 지금 뜨나

      • 용어 한 줄 — half-leading: line-height에서 글자 높이를 뺀 나머지를 위아래로 반씩 나눠 붙인 여백. 화면엔 안 보이지만 자리는 차지해서, 버튼·배지·제목이 “위로 뜬” 것처럼 보이게 만듭니다.
      • 지금까지 이걸 없애는 방법은 폰트별로 실측한 마이너스 마진이나 ::before/::after 해킹이었습니다. 폰트를 바꾸면 그 숫자가 전부 틀어졌고요.
      • 2025~2026년에 Chrome·Edge 133+, Safari 18.2+가 이 속성을 실어 보내면서, 디자인 시스템 쪽에서 “버튼 높이를 패딩으로 억지로 맞추는 시대”를 끝낼 수단으로 이야기되고 있습니다. (Firefox 지원 여부와 Baseline 단계는 자료마다 엇갈립니다 — 추정 확정하지 않고 아래 지원 배지로 실측하세요.)
      • 미지원 브라우저는 속성을 그냥 무시합니다. 예전 모양(여백 있는 상태)으로 보일 뿐 깨지지 않으므로 점진적 향상(progressive enhancement)의 교과서적 사례입니다.
      토글해 보세요 — 점선 박스가 실제 글자 상자입니다
      현재: text-box: normal
      ① 글자 상자 자체
      결제 완료

      파란 점선이 요소가 차지하는 높이. trim을 켜면 대문자/한글 윗선과 베이스라인에 딱 맞게 줄어듭니다.

      ② 배지·버튼 수직 정렬
      승인 부분취소

      trim을 켜면 padding이 “진짜 글자 기준” 여백이 됩니다. 그래서 값도 다시 잡아야 합니다(여기선 8px→12px).

      ③ 제목–본문 간격

      9월 정산 내역

      가맹점 3,112곳 · 승인 건 128,904건

      trim 전에는 margin-top:12px이 실제로 12px처럼 보이지 않습니다. 위아래 half-leading이 더해지니까요.

      실무 함정 — trim을 켜면 기존 padding·gap 값이 전부 “너무 좁아” 보입니다. 이건 버그가 아니라 드디어 지정한 값 그대로 렌더되는 상태입니다. 컴포넌트 단위로 켜고 패딩을 재보정하세요. 전역 * 셀렉터에 한 번에 켜는 건 위험합니다.

      💻 복붙용

      /* 단축 속성 text-box = text-box-trim + text-box-edge */
.btn, .badge, .stat-number {
  text-box: trim-both cap alphabetic;
  /* trim-both : 위아래 둘 다 자른다
     cap       : 위쪽은 대문자 높이(cap height) 기준으로 자른다
     alphabetic: 아래쪽은 베이스라인 기준으로 자른다 */
  padding-block: 12px;   /* trim 후엔 이 값이 '보이는 그대로'가 된다 */
}

/* 지원 브라우저에서만 여백을 다시 잡고 싶다면 */
@supports (text-box: trim-both cap alphabetic) {
  .btn { padding-block: 12px; }
}
@supports not (text-box: trim-both cap alphabetic) {
  .btn { padding-block: 9px; }   /* half-leading이 남아 있으니 덜 준다 */
}

      ♿ 접근성·주의

      • 터치 타깃 높이를 줄이지 마세요. trim으로 시각적 여백이 줄면 버튼이 작아 보여서 패딩을 더 주게 되는데, 그 방향이 맞습니다. 최소 44×44px 권장치는 그대로 지켜야 합니다.
      • 줄바꿈되는 본문 문단에는 쓰지 마세요. trim은 블록 컨테이너의 첫 줄 위 / 마지막 줄 아래만 자릅니다. 줄 사이 간격(line-height)은 그대로이므로 가독성에는 영향이 없지만, 본문에서 얻는 이득이 거의 없고 시각적 리듬만 흔들립니다. 한두 줄짜리 UI 텍스트에 쓰는 속성입니다.
      • 사용자가 브라우저 기본 글꼴 크기를 키웠을 때도 trim은 비율로 따라오므로 별도 대응은 필요 없습니다. 다만 px 고정 높이 버튼과 함께 쓰면 글자가 넘칩니다 — 높이는 min-height로.

      🧠 paysable 적용 포인트

      • 결제 화면의 금액 숫자 타일(큰 폰트 + 작은 라벨)이 가장 효과를 봅니다. 지금 마이너스 마진으로 맞춰 둔 곳이 있다면 @supports 분기로 걷어낼 후보입니다.
      • 디자이너가 Figma에서 준 “텍스트 상단 8px”은 사실 trim된 상자 기준인 경우가 많습니다. Figma도 자동 높이 텍스트에서 비슷한 트리밍 개념을 씁니다(추정 — 버전에 따라 다름). 그 간극이 “퍼블리싱이 시안이랑 미묘하게 다르다”의 정체인 경우가 있습니다.
      • 도입은 버튼 → 배지 → 금액 타일 순으로, 컴포넌트 단위로. 한 번에 전역 적용하면 회귀 스냅샷이 전부 깨집니다.
