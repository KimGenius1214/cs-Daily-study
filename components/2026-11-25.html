💳 해외 결제 통화 선택 — 기본값은 현지 통화, 원화(자국 통화)는 환율·마크업을 숫자로 보여준 뒤 고르게 결제·체크아웃

DCC(Dynamic Currency Conversion, 자국 통화 결제)는 해외 가맹점이 "원화로 바로 결제할래요?"라고 제안하는 서비스입니다. 편해 보이지만 가맹점 쪽 환율에 마크업이 붙고, 카드사 해외 이용 수수료는 그대로 붙는 경우가 많습니다. 그래서 요즘 체크아웃은 현지 통화를 기본으로 두고, 원화 쪽은 적용 환율·마크업·예상 차액을 숫자로 먼저 보여준 다음 사용자가 고르게 합니다.

시나리오를 바꿔 보세요 (모든 환율·수수료는 모의 값)

나쁨 자국 통화를 미리 골라 둔 버튼

결제 금액
편리한 자국 통화 결제가 적용됩니다 ·

환율도 마크업도 안 보이고, 현지 통화는 회색 작은 글씨 링크로 숨어 있습니다. 누르면 그냥 비싼 쪽으로 결제됩니다.

좋음 현지 통화 기본 + 숫자로 비교

어느 통화로 청구할까요?

기본 선택은 현지 통화. 자국 통화 쪽엔 적용 환율·기준 대비 마크업 %·예상 차액을 같이 적고, 버튼 문장이 실제 청구 통화와 금액을 그대로 말합니다.

// 금액 계산은 정수 최소단위(minor unit)로 — 부동소수점 금지
const minor = { KRW: 0, USD: 2 };                       // 통화별 소수 자릿수
const fmt = (v, cur) => new Intl.NumberFormat('ko-KR', {
  style: 'currency', currency: cur, maximumFractionDigits: minor[cur]
}).format(v);

// rate: 카드 통화 / 가맹점 통화 1단위,  markup: DCC 제공사 가산율
function quote(amount, rate, markup, cardFee) {
  const local = amount * rate * (1 + cardFee);           // 현지 통화 청구 → 카드사가 환전 (예상치)
  const dcc   = amount * rate * (1 + markup) * (1 + cardFee); // 자국 통화로 확정
  return { local, dcc, diff: dcc - local };
}
현지 통화로 청구하면 원화 금액은 카드사가 매입 시점 환율로 정하므로 결제 화면에선 "예상"일 수밖에 없습니다. 반대로 DCC는 금액이 결제 순간 확정되는 대신 비쌉니다. 그래서 좋은 화면은 현지 통화 쪽 원화 금액에 "약·예상"을 붙이고, DCC 쪽엔 "확정"을 붙입니다. 카드 브랜드 규정상 DCC는 고객이 명시적으로 고르게 하고 환율·마크업을 고지하도록 요구하는 것으로 알려져 있습니다(정확한 조건은 가맹점·PG 계약 확인 필요, 추정).

⌨️ 모바일 키보드 고르기 — inputmode는 자판, enterkeyhint는 엔터 라벨, autocomplete는 자동 채움, 숫자 "번호"에 type=number는 쓰지 않기 입력·폼

모바일 결제 폼에서 체감 속도를 가장 크게 바꾸는 건 디자인이 아니라 어떤 자판이 뜨느냐입니다. inputmode(어떤 가상 키보드를 띄울지 힌트), enterkeyhint(엔터 키에 "다음·완료·검색" 같은 라벨을 붙이는 힌트), autocomplete(브라우저·OS 자동 채움이 어떤 값을 넣을지 알려 주는 토큰) 세 가지를 필드마다 맞춰 줍니다. 단, enterkeyhint는 라벨만 바꿉니다 — 엔터를 눌렀을 때 다음 칸으로 가는 동작은 직접 만들어야 합니다.

좋음 엔터 동작은 직접 만든다

위 폼에서 엔터를 누르면 다음 칸으로 갑니다(마지막 칸에서만 제출). 폼 안 입력칸에서 엔터는 원래 암묵적 제출(implicit submission, 엔터만으로 폼이 제출되는 기본 동작)을 일으키기 때문에, 막지 않으면 카드 번호 치다가 결제가 눌립니다. 한글 조합 중(e.isComposing) 엔터는 건드리지 않습니다.

<input inputmode="numeric" autocomplete="cc-number" enterkeyhint="next">

// enterkeyhint는 라벨만 — 동작은 직접
form.addEventListener('keydown', (e) => {
  if (e.key !== 'Enter' || e.isComposing || e.target.tagName === 'TEXTAREA') return;
  const fields = [...form.querySelectorAll('input:not([type=hidden]):not(:disabled)')];
  const i = fields.indexOf(e.target);
  const hint = e.target.enterKeyHint;
  if (hint === 'next' && i > -1 && i < fields.length - 1) {
    e.preventDefault();              // 암묵적 제출 막기
    fields[i + 1].focus();
  }
});
enterkeyhint는 Chromium·Safari 계열에서 지원되며, 데스크톱 브라우저에선 보이는 차이가 없습니다. Firefox 지원 여부는 버전별로 확인이 필요합니다(추정). 모든 속성은 힌트라서 안 먹는 환경에서도 폼이 깨지지 않는 게 장점입니다. 참고: MDN enterkeyhint.

🌀 페이지 간 View Transitions — 진짜 페이지 이동(MPA)에도 @view-transition 한 줄로 목록→상세 연결 애니메이션 트렌드

지난번까지 다룬 View Transitions는 한 페이지 안에서 DOM을 바꿀 때(document.startViewTransition())였습니다. 교차 문서(cross-document) 전환은 링크를 눌러 새 HTML 문서로 이동할 때도 같은 효과를 줍니다. 두 페이지 모두에 @view-transition { navigation: auto }를 넣고, 이어지는 요소에 같은 view-transition-name을 주면 브라우저가 이전 화면 스냅샷과 새 화면을 이어 붙입니다. 같은 출처(origin) 이동에만 적용됩니다.

가맹점 카드를 눌러 보세요 — 실제로 새 문서를 불러오는 페이지 이동입니다 (뒤로 가기도 해 보세요)

/* 두 문서(목록·상세) 모두에 */
@media (prefers-reduced-motion: no-preference) {
  @view-transition { navigation: auto; }
}
/* 목록의 썸네일과 상세의 히어로에 같은 이름 → 이어지는 모핑 */
.card[data-id="a"] .thumb { view-transition-name: m-a; }
.detail .hero             { view-transition-name: m-a; }
::view-transition-group(*) { animation-duration: .38s; }

// 선택: 새 문서 쪽에서 전환 직전에 개입
window.addEventListener('pagereveal', (e) => {
  if (!e.viewTransition) return;            // 미지원·첫 진입이면 null
  e.viewTransition.types?.add(isBack ? 'back' : 'forward');
});
지원 현황(2026-11 기준 확인 수준): Chromium 계열과 Safari는 지원, Firefox는 진행 중으로 알려져 있습니다(추정 — caniuse에서 확인). 미지원 브라우저에선 그냥 평소처럼 페이지가 바뀌므로 점진적 향상(progressive enhancement, 되는 곳에서만 더 좋아지고 안 되는 곳에서도 기능은 그대로)입니다. 이 데모를 file://로 열면 출처가 불투명해 전환이 안 될 수 있습니다 — GitHub Pages 주소에서 확인하세요. 참고: Chrome 문서.
