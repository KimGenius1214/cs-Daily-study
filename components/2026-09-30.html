💳 부분 환불 요청 ⌨️ 정산 계좌·예금주 확인 🌀 CSS @function

💳 부분 환불 요청 — 환불 가능 잔액을 먼저 보여주고, 차감은 줄 단위로, 확정은 금액을 말하는 버튼으로 결제·체크아웃 UX

결제 취소는 "전액 취소" 버튼 하나면 끝나지만, 부분 환불은 얼마까지 되나 · 무엇이 빠지나 · 어디로 돌아가나 세 질문에 답해야 한다. 아래는 이미 한 번 부분 환불된 주문(결제 89,000원, 기환불 12,000원)이다.

라이브 — 품목을 고르거나 금액을 직접 넣어 보세요 (한도 초과·무료배송 조건 깨짐·사유 누락까지)

주문 #PA-240930-0172

    부분 금액 환불은 품목과 무관한 보상·가격 조정용. 배송비 정책은 적용하지 않습니다.

    환불 사유를 선택해 주세요.

    환불 가능 잔액

    기환불 12,000이번 환불남는 잔액

    잔액 막대는 "앞으로 얼마까지 되나"를 먼저 보여준다. 합계는 줄 단위 차감(반품 배송비 등)을 거친 실제 돌려받는 돈이고, 버튼 문구가 그 금액을 그대로 말한다.

    환불을 확정할까요?

    변형 비교

    변형언제핵심
    품목·수량 선택반품·부분 취소수량 스테퍼, 이미 환불된 수량은 잠금, 배송비 조건 재계산
    금액 직접 입력보상·가격 조정상한 = 결제액 − 기환불액, "최대" 칩, 초과 시 즉시 인라인 에러
    전액 취소(대조군)미배송·당일 취소부분 환불 UI를 거치지 말고 별도 1-스텝 경로로

    코드 — 상한·차감·배분 계산 (순수 함수로 분리)

    // 금액은 전부 원 단위 정수. 화면 서식은 표시 단계에서만.
export function calcRefund({ paid, refunded, lines, mode, amount, reason, policy }) {
  const cap = paid - refunded;                         // 환불 가능 잔액
  const gross = mode === 'amount' ? amount
    : lines.reduce((s, l) => s + l.price * l.qty, 0);
  const deductions = [];
  if (mode === 'item' && reason === 'cs' && policy.breaksFreeShipping(lines))
    deductions.push({ label: '반품 배송비', amount: policy.returnFee });
  const net = gross - deductions.reduce((s, d) => s + d.amount, 0);
  const error = net > cap ? 'OVER_CAP' : net <= 0 ? 'EMPTY' : null;
  // 배분: 가맹점 정책 예 — 카드 먼저, 부족분은 포인트
  const toCard = Math.min(net, policy.cardLeft);
  return { cap, gross, deductions, net, error,
           alloc: [{ via: '카드', amount: toCard }, { via: '포인트', amount: net - toCard }] };
}

    접근성·상태

    • 합계가 바뀔 때 aria-live="polite"로 "환불 예정 23,000원" 한 문장만 읽힘(표 전체를 다시 읽히지 않음).
    • 확정 버튼은 disabled 대신 aria-disabled — 포커스는 받고, 누르면 막힌 이유(사유 미선택 등)로 이동.
    • 확인 다이얼로그는 기본 포커스를 "돌아가기"에 — 되돌릴 수 없는 액션이므로 Enter 연타로 확정되지 않게.
    배분 순서(카드 먼저/포인트 먼저)와 반품 배송비 규칙은 가맹점·PG 정책마다 다른 예시값이다. 규칙은 서버가 계산해 내려주고, 프론트는 같은 순수 함수로 "미리보기"만 한다는 전제.

    ⌨️ 정산 계좌 입력과 예금주 확인 — 은행 칩·번호 정규화·실명조회 상태머신 입력·폼

    정산 계좌는 "형식이 맞다"와 "진짜 그 사람 계좌다"가 다른 문제다. 입력 → 형식 검증 → 예금주 조회(실명조회) → 일치/불일치/점검 중 분기. 그리고 확인 후 한 글자라도 바꾸면 확인은 무효가 되어야 한다.

    라이브 — 은행·번호를 넣고 "예금주 확인" (아래 시뮬레이터로 서버 응답을 바꿔 보세요)

    은행

    붙여넣기 시 하이픈·공백은 자동 제거됩니다.

    사업자 등록 정보에서 가져온 값(데모에선 수정 가능).

    서버 응답 시뮬레이터:
    대기은행과 계좌번호를 입력하면 확인할 수 있어요.
    idle→ready→checking→matched/mismatch/notfound/maint/limit · 수정 시 stale

    저장 버튼은 matched일 때만 활성. 확인 후 번호를 고치면 즉시 stale(재확인 필요)로 내려간다 — "확인된 계좌 ≠ 저장될 계좌" 사고를 막는 핵심.

    상태별 설계

    상태보여줄 것주 액션
    mismatch조회된 예금주 마스킹(김*수) — 전체 노출 금지번호 다시 입력 / 법인·공동명의면 증빙 제출
    notfound은행·번호 조합을 다시 보라는 안내번호 필드로 포커스
    maint은행 점검 시간대(은행별 상이) 안내"임시 저장 후 자동 재확인" 또는 나중에
    limit남은 대기 시간카운트다운 후 재시도 (무차별 조회 방지)

    코드 — 정규화 + 스테일 처리

    const normalize = (s) => s.normalize('NFKC').replace(/[^0-9]/g, '');   // 전각 숫자·하이픈·공백 제거

let verifiedKey = null;                     // 확인 당시의 (은행+번호) 스냅샷
function onInput() {
  const key = `${bank}:${normalize(acc.value)}`;
  if (verifiedKey && key !== verifiedKey) setState('stale');   // 바꾸면 확인 무효
}
async function verify() {
  const key = `${bank}:${normalize(acc.value)}`;
  setState('checking');
  const res = await api.verifyAccount({ bank, account: normalize(acc.value) });
  if (`${bank}:${normalize(acc.value)}` !== key) return;        // 응답 도착 전에 바뀌었으면 버림
  verifiedKey = res.status === 'matched' ? key : null;
  setState(res.status, res);
}

    접근성·상태

    • 은행 칩은 fieldset + radio — 화살표 키로 이동하는 네이티브 라디오 그룹을 그대로 씀(커스텀 div 버튼 금지).
    • 상태 박스는 role="status": "확인 중 → 일치" 전환을 스크린리더가 읽음. 실패 시 주 액션 버튼에 포커스 이동.
    • inputmode="numeric"(모바일 숫자 키패드 요청 속성) + type="text" — 앞자리 0이 사라지는 type="number"는 계좌번호에 쓰지 않는다.
    예금주 조회 API의 응답 코드·점검 시간·조회 횟수 제한은 제공사(은행·펌뱅킹·오픈뱅킹 대행사)마다 다르다. 위 상태 이름은 예시이며, 실제 매핑은 연동 문서 기준으로 맞출 것(추정).

    🌀 CSS @function — 토큰 계산을 CSS 안의 함수로, 그리고 var()가 끼면 폴백이 안 먹는 함정 트렌드·개념

    @function은 인자를 받아 값을 돌려주는 CSS 사용자 정의 함수. Sass 믹스인·함수로 빌드 타임에 하던 "간격 = n×4px", "상태색의 연한 배경" 같은 계산을 런타임 CSS가 직접 한다. Chrome 139부터 지원, Firefox·Safari는 아직(Safari는 Tech Preview 단계).

    지원 여부 확인 중…

    ① --tint(색, 비율) — 상태 배지 배경을 한 함수로 (슬라이더로 비율 조절)

    결제 완료승인 대기 결제 실패부분 환불
    14%

    ② --space(n) — 4px 그리드 간격 스케일

    막대 높이 = --space(1·2·4·6·10·16). 미지원이면 옆에 적어 둔 px 폴백으로 동일하게 보임(인자에 var()가 없어서 파싱 폴백이 동작).

    ③ --fluid(min, max) — 담긴 칸 폭에 맞춰 크는 금액 글자 (오른쪽 아래 모서리로 폭 조절)

    ₩1,284,000
    clamp(18px, 3.2cqi, 36px)

    ④ 폴백 함정 — 세 가지 쓰는 법, 미지원 브라우저에서 결과가 갈린다

    naive: 폴백 줄 + --tint(var(..)) bad: --bg: --tint(..) good: html.fn-ok 가드

    📈 왜 지금 뜨나 / 어디에 쓰나

    • 디자인 토큰의 "계산"까지 CSS로: 브랜드·상태색은 변수로, 파생(연한 배경·테두리·호버)은 함수로. 테마 전환 시 다시 빌드할 필요가 없다.
    • if()·color-mix()·컨테이너 단위와 조합: 어제 본 if()를 함수 안에 넣으면 조건부 토큰 함수가 된다.
    • 타입 선언(--c <color>, returns <length>): 잘못된 타입 인자는 무효 처리 — 느슨한 var()보다 안전.

    코드

    @function --tint(--c <color>, --p <percentage>: 14%) returns <color> {
  result: color-mix(in oklab, var(--c) var(--p), var(--surface));
}
@function --space(--n <number>) returns <length> { result: calc(var(--n) * 4px); }

/* ✅ 인자에 var() 없음 → 미지원 브라우저는 파싱 단계에서 버리고 윗줄 유지 */
.gap { height: 16px; height: --space(4); }

/* ❌ 인자에 var() 있음 → 파싱 통과 후 계산 시점에 무효 → unset (폴백 줄 무시됨) */
.badge { background: var(--ok-soft); background: --tint(var(--ok)); }

/* ✅ 기능 감지 클래스(또는 @supports)로 가드 */
html.fn-ok .badge { background: --tint(var(--ok)); }
    왜 naive가 깨지나: 선언 값에 var()가 하나라도 있으면 브라우저는 그 선언을 파싱 시점에 검증하지 않고 "나중에 치환"으로 받아 둔다. 그래서 앞 줄 폴백을 덮어쓴 뒤, 계산 시점에 모르는 함수를 만나 unset이 된다. 어제 if()와 같은 계열의 함정. @supports로 @function을 감지하는 확실한 문법은 브라우저 지원이 엇갈려(추정) 데모는 JS 탐지 클래스를 썼다.
