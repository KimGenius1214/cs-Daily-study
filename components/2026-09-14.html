⌨️ 이메일·태그 토큰 입력 입력·폼

"여러 명 초대", "정산 알림 받을 주소 등록", "태그 달기" 같은 칸은 값이 여러 개다. 그런데 흔히 <input type="text"> 하나에 "쉼표로 구분해 입력하세요"라고 적어두고 끝낸다. 사용자는 그 문장을 안 읽고, 엑셀에서 복사한 줄바꿈 목록을 그대로 붙여넣고, 어디가 틀렸는지도 모른 채 제출한다. 토큰(칩) 입력은 확정된 값 하나하나를 눈에 보이는 조각으로 만들어, 개수·중복·오류를 제출 전에 보여준다.

변형 A — 토큰 입력 (Enter · 쉼표 · 세미콜론 · 스페이스로 확정, ← → 로 칩 이동, Backspace로 삭제)

쉼표·세미콜론·스페이스·Enter로 확정됩니다. 여러 줄 붙여넣기도 자동 분리합니다. 0 / 8명

아직 입력이 없습니다.

확정된 값은 파란 칩, 형식이 틀리면 빨간 물결 밑줄 칩, 이미 있는 주소면 노란 칩으로 즉시 구분된다. 틀린 칩은 클릭하면 다시 편집 상태로 풀려서, 지우고 다시 치지 않아도 된다.

붙여넣기 원본 (위 버튼이 이 텍스트를 그대로 붙여넣는다)

줄바꿈·쉼표·세미콜론·중복·공백이 뒤섞인 현실의 목록이다. 붙여넣기 한 번에 분리 → 공백 제거 → 중복 표시 → 형식 검사까지 끝나야 한다.

변형 B — 흔한 방식 (비교용): 텍스트 한 칸 + "쉼표로 구분하세요"

여기에 같은 목록을 붙여넣어 보세요. 줄바꿈이 사라지고, 몇 명인지·어디가 틀렸는지 알 수 없습니다.

같은 데이터를 넣어도 제출 버튼을 누르기 전까지 아무 것도 알 수 없다. 서버가 400을 돌려준 뒤에야 "형식이 올바르지 않습니다"를 본다.

♿ 접근성·상태 설계

  • 칩도 키보드로 닿아야 한다. 칩에 tabindex="0"을 주지 말고, 입력창에서 ←→로 칩 사이를 옮겨 다니게 하는 편이 Tab 횟수를 줄인다(오늘 데모 방식).
  • Backspace 2단계: 입력창이 비었을 때 첫 Backspace는 마지막 칩을 선택만 하고, 한 번 더 눌러야 지운다. 한 번에 지우면 실수로 사라진다.
  • role="status" + aria-live="polite"(= 화면이 바뀌면 스크린리더가 하던 말을 끊지 않고 이어서 읽어주는 영역)로 "3명 추가됨, 1건 중복"을 알린다. 칩만 늘어나면 눈으로 보는 사람만 안다.
  • 오류는 칩 색만으로 말하지 않는다. 빨강 + 물결 밑줄 + 하단 텍스트 요약 3중으로. 색만 쓰면 색각 이상 사용자에게 아무 정보가 아니다.
  • 한도 초과는 입력을 막지 말고 알린다. 8명 한도면 9번째 입력 자체를 차단하기보다, 넣게 두고 "8명까지만 저장됩니다"를 보여주는 쪽이 덜 답답하다(오늘 데모는 상자 테두리를 빨갛게).

💻 코드 (복붙용) — 붙여넣기 분리와 중복 판정

const SPLIT = /[\s,;]+/;                       // 공백·줄바꿈·쉼표·세미콜론 전부 구분자로
const EMAIL = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;    // 화면용 1차 검사. 최종 판정은 서버가 한다

function ingest(raw, existing) {
  const seen = new Set(existing.map(t => t.value.toLowerCase()));
  return raw.split(SPLIT).filter(Boolean).map(v => {
    const key = v.toLowerCase();
    const state = seen.has(key) ? 'dupe' : EMAIL.test(v) ? 'valid' : 'invalid';
    if (state === 'valid') seen.add(key);
    return { value: v, state };
  });
}

input.addEventListener('paste', (e) => {
  const text = e.clipboardData.getData('text');
  if (!SPLIT.test(text)) return;               // 구분자가 없으면 평범한 붙여넣기로 둔다
  e.preventDefault();
  addTokens(ingest(text, tokens));
});
왜 붙여넣기부터 챙기나 — 이런 칸에 값을 넣는 사람은 대부분 어딘가에서 복사해 온다(엑셀 열, 슬랙 메시지, 기존 설정 화면). 한 글자씩 타이핑하는 경로만 만들어 두면 가장 흔한 경로가 가장 안 되는 경로가 된다.

🔘 비활성 버튼 다시 설계하기 버튼·액션

조건이 안 맞으면 버튼을 disabled로 잠그는 건 반사적인 선택이다. 그런데 disabled 버튼은 포커스를 받지 못하고, 마우스 이벤트도 발생하지 않고, 툴팁도 못 띄우고, 스크린리더 탐색에서도 사실상 지나쳐진다. 사용자는 "왜 못 누르는지" 물어볼 대상 자체를 잃는다. 요즘은 버튼은 살려 두고, 누르면 막힌 이유로 데려가는 쪽으로 간다.

아래 조건을 만족해야 결제가 가능하다. 조건을 안 채운 채로 세 버튼을 각각 Tab과 클릭으로 눌러보라.

    처리 중일 때는? — aria-disabled + aria-busy

    결제 조건을 모두 채우면 이 버튼이 실제로 눌립니다.

    처리 중에는 버튼 라벨을 "처리 중…"으로 바꾸고 aria-disabled="true" aria-busy="true"를 건다. 버튼 폭을 고정해 글자가 바뀔 때 레이아웃이 튀지 않게 하는 것도 같이 챙긴다.

    상황권장메모
    필수 입력이 안 찼다aria-disabled + 이유 사용자가 고칠 수 있는 문제. 데려가 주는 게 맞다

// 처리 중: disabled 로 바꾸지 않는다(포커스가 사라진다)
function setBusy(on) {
  btn.setAttribute('aria-disabled', String(on));
  btn.setAttribute('aria-busy', String(on));

}

    ♿ 접근성 메모

    • aria-disabled는 "보기에만" 비활성이다. 실제 동작 차단은 반드시 JS(그리고 서버)가 해야 한다. 속성만 걸고 방치하면 진짜로 결제가 나간다.
    • 대비(contrast): disabled인 진짜 비활성 요소는 WCAG 대비 기준의 예외로 다뤄지지만, aria-disabled는 여전히 조작 가능한 요소다. 너무 흐리게 만들지 말고 opacity:.6 선에서 멈추는 게 안전하다.
    • 포커스 링은 남긴다. 흐린 버튼이라도 포커스 시 테두리가 보여야 키보드 사용자가 위치를 잃지 않는다.
    • 이유 영역은 aria-describedby로 버튼에 묶는다. 화면 어딘가에 뜨기만 해서는 스크린리더가 버튼과 연결 짓지 못한다.

    🧠 paysable 적용 포인트

    • 결제/정산 실행 버튼: 약관 미동의·금액 0원·수단 미선택은 전부 "고칠 수 있는" 문제다. 잠그기보다 데려가기.
    • 중복 결제 방지: 처리 중 상태는 disabled가 아니라 aria-disabled + aria-busy + 멱등키(같은 요청을 두 번 받아도 한 번만 처리하게 하는 서버 쪽 키)로.
    • 권한 기반 화면: 가맹점 운영자에게 관리자 전용 버튼을 흐리게 보여주는 대신, 아예 감추고 "권한이 필요합니다" 안내로 대체.

    🌀 text-box-trim — 글자 위아래 여백을 잘라 정렬 맞추기 트렌드·개념

    버튼 안 글자가 살짝 위로 뜬 것 같아서 padding-top: 13px; padding-bottom: 15px처럼 홀수로 맞춰본 적이 있다면, 범인은 눈이 아니라 폰트가 글자 위아래에 갖고 있는 빈 공간이다. text-box-trim은 그 빈 공간을 잘라내서, "대문자 윗선(cap)"과 "기준선(baseline)"을 상자 경계로 삼게 해준다.

    📈 왜 지금 뜨나 / 어디에 쓰나

    • half-leading(= line-height가 글자 크기보다 클 때 위아래로 절반씩 나눠 붙는 여백)과 폰트의 ascender/descender 공간 때문에, 글자 상자는 항상 글자보다 크다. 디자이너의 Figma 값과 개발자의 CSS 값이 안 맞는 고전적 원인이 이것이다.
    • 지금까지의 해법은 매직 넘버였다. 폰트를 바꾸면 전부 다시 맞춰야 했고, 한글·영문이 섞이면 또 달라졌다.
    • 디자인 시스템 관점에서 진짜 이득은 "padding 값이 곧 시각적 여백"이 된다는 점이다. 토큰(8/12/16px)을 그대로 쓰면 되고, 리뷰에서 "1px만 내려주세요"가 사라진다.
    • 단, 여백이 사라지므로 padding을 다시 설계해야 한다. trim만 켜면 버튼이 갑자기 납작해 보인다 — 그만큼 padding을 늘려야 한다.

    💻 코드 (복붙용)

    /* 축약형 — 위아래 모두 자르고, 대문자 윗선 ~ 기준선을 경계로 */
.btn { text-box: trim-both cap alphabetic; }

/* 풀어 쓰면 */
.btn {
  text-box-trim: trim-both;        /* trim-start | trim-end | trim-both | none */
  text-box-edge: cap alphabetic;   /* 시작 경계 | 끝 경계 */
}

/* 안전하게: 지원하는 브라우저에서만 padding까지 같이 바꾼다 */
.btn { padding: 12px 20px; }
@supports (text-box: trim-both cap alphabetic) {
  .btn { text-box: trim-both cap alphabetic; padding: 15px 20px; }
}
    한글에서 주의 — cap alphabetic은 라틴 문자의 대문자 높이와 기준선을 기준으로 삼는다. 한글은 대문자/소문자 구분이 없고 글자가 기준선 아래로 거의 내려가지 않아 결과가 폰트마다 다르게 보일 수 있다(추정 — 프로젝트에서 쓰는 폰트로 직접 확인 권장). text-box-edge: text text(글자 상자 그대로) 같은 다른 값도 비교해 보고 정하는 게 안전하다.

    🧠 paysable 적용 포인트

    • 금액 표시: 숫자만 있는 큰 텍스트는 위아래 여백 차이가 특히 도드라진다. 대시보드 KPI 숫자에 먼저 적용해 보기 좋다.
    • 버튼·배지·칩: 디자인 시스템의 높이 토큰(32/40/48px)을 만들 때 매직 넘버를 없앨 수 있다.
    • 도입 방식: 전역 리셋에 한 번에 넣지 말고 @supports + 컴포넌트 단위로. Firefox 사용자에게 레이아웃이 무너지지 않는지가 유일한 판단 기준이다.
