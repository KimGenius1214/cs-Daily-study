📊 시계열 차트 — 보여주는 게 아니라 읽게 만들기 데이터·테이블·차트

대시보드에 선 하나 그려놓으면 "추세"는 전달되지만 "9월 11일에 정확히 얼마였나"는 전달되지 않는다. 2026년 기준 잘 만든 차트의 공통점은 셋이다 — ① 마우스뿐 아니라 키보드로도 값을 훑을 수 있고, ② 데이터가 없는 구간을 0으로 속이지 않고 끊어서 보여주고, ③ 같은 데이터를 표로도 내려받거나 펼칠 수 있다. (aria-live = 화면을 다시 안 읽어도, 그 영역의 글자가 바뀌면 스크린리더가 알아서 읽어주는 영역.)

변형 A — 스파크라인 KPI 카드 (읽는 차트가 아니라 "느끼는" 차트)

축도 툴팁도 없다 · 방향과 최근 변동만

스파크라인(sparkline: 축·눈금 없이 숫자 옆에 붙이는 미니 추세선)은 값을 읽히려는 물건이 아니다. 그래서 툴팁·호버를 달지 않고, 대신 숫자·델타 배지가 정확한 값을 책임진다. SVG에는 aria-hidden="true"를 주고 카드 전체를 한 문장으로 읽히게 하는 편이 스크린리더에 훨씬 낫다.

변형 B — 값 커서가 있는 선 차트 (마우스 + 키보드 동일 동작)

차트를 클릭하거나 Tab으로 포커스 → ← → 이동 · Home End 양끝

—

포커스 링이 차트 전체에 한 번만 생기고, 그 안에서 화살표로 점을 옮긴다(로빙 포커스). 점 14개를 전부 tabindex="0"으로 만들면 Tab을 14번 눌러야 하므로 실무에선 거의 항상 이 형태다. 읽어주는 문장은 눈에 보이는 판독창(readout)과 같은 요소라, 보는 사람과 듣는 사람이 같은 정보를 받는다.

변형 C — 같은 데이터, 표로 보기 (차트의 대체 표현)

"그림이 안 보이는 사람"이 아니라 "숫자를 정확히 원하는 사람"을 위한 것이기도 하다

일별 결제 승인액 (단위: 백만원) · 결측은 0이 아니라 “—”
날짜승인액전일 대비

결측일(9/13)을 0으로 채우면 "장사를 아예 못 한 날"이 되어버린다. 선을 끊고 점선으로 잇고, 표에는 —와 사유를 남긴다. 결제 도메인에서 이 구분은 그냥 UX가 아니라 사고 예방이다.

구현 노트. 라이브러리를 쓰든 말든 위 세 가지는 라이브러리가 대신 해주지 않는다. 차트 라이브러리를 고를 때 "예쁜가"보다 키보드 탐색·대체 표 출력을 기본 제공하는가를 먼저 본다(추정: 라이브러리별 지원 편차가 크다). 직접 SVG로 그리면 이 데모처럼 200줄 안쪽으로 끝나기도 한다.

💻 코드 — 키보드 커서 + 라이브 판독창

<div class="ts-chart" tabindex="0" role="group"
     aria-label="일별 승인액 선 차트. 좌우 화살표로 값을 읽습니다."
     aria-describedby="readout">
  <svg aria-hidden="true"><!-- 선·점·커서 --></svg>
</div>
<p id="readout" role="status" aria-live="polite">9월 17일 · 276백만원 · 전일 대비 -8.6%</p>

<script>
chart.addEventListener('keydown', (e) => {
  const step = { ArrowRight: 1, ArrowLeft: -1 }[e.key];
  let next = null;
  if (step) next = Math.min(data.length - 1, Math.max(0, cursor + step));
  else if (e.key === 'Home') next = 0;
  else if (e.key === 'End') next = data.length - 1;
  if (next === null) return;
  e.preventDefault();          // 페이지 가로 스크롤 방지
  cursor = next;
  render();                    // 커서선 이동 + readout 텍스트 교체 → 자동으로 읽힘
});
</script>

♿ 접근성·상태 설계

  • 차트 하나 = 포커스 하나. 내부 점은 화살표로 이동(로빙 포커스). Tab 지옥을 만들지 않는다.
  • 판독창은 role="status"(= aria-live="polite"). 화살표를 빠르게 연타해도 읽던 걸 끊지 않는다. 긴급 알림이 아니므로 assertive는 쓰지 않는다.
  • 장식 SVG는 aria-hidden="true", 정보 SVG는 role="img" + 요약 aria-label. 둘을 섞으면 스크린리더가 좌표를 읽는다.
  • 색으로만 구분하지 않기. 상승·하락은 색 + 화살표 + 부호(＋/−)를 함께 쓴다(WCAG 1.4.1 감각 특성 의존 금지).
  • 결측 ≠ 0. 점선·빈 점·표의 “—”로 셋 다 동일하게 표기한다.
  • 숫자는 font-variant-numeric: tabular-nums(숫자 폭 고정)로 커서를 옮겨도 자릿수가 덜컹거리지 않게.

🧠 paysable 적용 포인트

  • 정산·매출 대시보드: 막대/선 위에 키보드 커서 + 판독창만 얹어도 "값을 확인하려고 표로 내려가는" 왕복이 사라진다.
  • 집계 배치가 지연된 날은 선을 끊는다. 0으로 이어 그리면 CS 문의가 "결제가 안 됐나요"로 바뀐다.
  • 가맹점에 내보내는 리포트는 차트↔표 토글 + CSV 복사를 기본 세트로. 회계 담당자는 결국 숫자를 복사한다.

🔔 “아직 확정 아님”을 말해주는 상태 — 배지 어휘와 처리 타임라인 피드백·상태(로딩·빈상태·에러)

결제는 버튼을 누른 순간 끝나지 않는다. 승인(authorized) → 매입(captured) → 정산(settled)까지 며칠이 걸리는데, 화면이 "완료"만 보여주면 사용자는 이미 끝난 줄 알고 환불·취소 문의를 한다. 요즘 패턴은 중간 상태를 숨기지 않고 어휘로 정리하고, 각 상태마다 지금 할 수 있는 일을 함께 보여주는 것이다.

    변형 C — 목록에서의 상태 (polling 갱신을 조용히)

    "시작"을 누르면 3초마다 상태가 갱신됩니다 · 토스트 폭탄 없이

    마지막 갱신: —

    목록 폴링(polling: 일정 간격으로 서버에 다시 물어보기)의 함정은 바뀔 때마다 토스트를 띄우는 것이다. 행 안에서 배지만 조용히 바뀌게 하고, 스크린리더에는 요약 한 줄만(“2건이 매입 완료로 바뀌었습니다”) 알린다.

    💻 코드 — 상태 어휘를 한 곳에 모으기

    // 상태는 색이 아니라 "표시 문구 + 아이콘 + 가능한 행동"의 묶음이다.
export const TXN_STATUS = {
  pending:    { label: '결제 대기',        tone: 'wait', icon: '◌', actions: ['resend'] },
  authorized: { label: '승인 완료(미매입)', tone: 'auth', icon: '🔒', actions: ['capture', 'void'] },
  capturing:  { label: '매입 처리 중',      tone: 'prog', icon: null, actions: [] },   // 취소 버튼을 열지 않는다
  settled:    { label: '정산 완료',        tone: 'done', icon: '✓', actions: ['refund'] },
  declined:   { label: '승인 거절',        tone: 'fail', icon: '!', actions: ['reason', 'retry'] },
} as const;

// 화면은 상태를 "번역"만 하고 판단은 하지 않는다 → 새 상태가 생겨도 UI는 한 곳만 고친다
<Badge tone={TXN_STATUS[s].tone} icon={TXN_STATUS[s].icon}>{TXN_STATUS[s].label}</Badge>

    ♿ 접근성·상태 설계

    • 배지는 색 + 아이콘 + 텍스트 3중. 색만으로 구분되면 색각 이상 사용자에게 6개 상태가 3개로 보인다.
    • 스피너 아이콘은 aria-hidden, 상태 변화는 텍스트로 알린다. 회전만으로는 아무것도 전달되지 않는다.
    • 현재 단계에 aria-current="step", 완료 단계엔 ✓를 텍스트 대체와 함께.
    • 폴링 갱신은 polite로 묶어서 한 문장. 행마다 live 영역을 두면 스크린리더가 끊임없이 떠든다.
    • prefers-reduced-motion(= OS에서 "동작 줄이기"를 켠 사용자) 에서는 스피너 회전을 점멸 없는 정적 표시로 낮춘다.

    🧠 paysable 적용 포인트

    • 거래 상세/목록의 상태 문자열이 컴포넌트마다 흩어져 있으면, 위처럼 단일 맵(TXN_STATUS)으로 모아 버튼 노출까지 파생시킨다.
    • "매입 처리 중"에 취소 버튼을 노출하지 않는 것 자체가 UX다 — 눌러도 실패할 버튼은 실패 응답보다 나쁘다.
    • 가맹점 정산 화면: 단계별 예상 입금일을 기울임 표기로 붙이면 "언제 들어오나요" 문의가 줄어든다(추정).

    🌀 sibling-index() · sibling-count() — 순번을 드디어 CSS가 안다 트렌드·개념

    지금까지 리스트 스태거(stagger: 항목을 한 박자씩 밀어서 등장시키기)를 하려면 JS로 style.setProperty('--i', i)를 돌리거나 :nth-child(1..20)을 손으로 깔아야 했다. sibling-index()는 "나는 형제 중 몇 번째인가"를, sibling-count()는 "형제가 총 몇 개인가"를 CSS 안에서 숫자로 돌려준다. 항목이 늘거나 줄어도 CSS가 알아서 다시 계산한다.

    변형 A — 스태거 등장 (JS 인덱스 주입 없음)

    항목을 추가/삭제해도 지연 시간은 CSS가 다시 계산

      transition-delay: calc(sibling-index() * 55ms) 한 줄이 전부다. JS는 .play 클래스만 토글한다 — 인덱스를 세거나 DOM을 순회하지 않는다.

      변형 B — sibling-count()로 "개수에 맞춰" 분배

      색 농도와 막대 길이를 전체 개수 대비 비율로

      진행 단계 램프 — sibling-index() / sibling-count()

        막대 길이도 같은 식으로

          개수가 바뀌면 비율이 통째로 다시 잡힌다. 예전엔 "5단계일 때 20%씩"을 하드코딩하거나 JS로 계산했다.

          변형 C — 폴백과 감속

          지금 이 브라우저의 지원 여부

          ✅ 이 브라우저는 sibling-index()를 지원합니다 — 위 데모가 순차로 등장하고, 램프 색이 단계별로 진해집니다.

          ⚠️ 이 브라우저는 sibling-index()를 아직 지원하지 않습니다 — 스태거 없이 전부 동시에 등장하고, 램프는 회색 균일입니다. 이게 바로 의도한 폴백입니다.

          @supports (transition-delay: calc(sibling-index() * 1ms))로 감싸면, 미지원 브라우저는 "지연 0 = 전부 동시 등장"이라는 멀쩡한 결과를 받는다. 스태거는 없어도 되는 장식이므로 이 폴백이면 충분하다.

          🌐 지원 현황(2026-09 기준, 일부 추정). Chromium 계열(Chrome/Edge) 138+에서 먼저 출시됐고 Safari 26.x 라인에서 뒤따랐다. Firefox는 구현 작업 중이나 정식 출시 여부는 확인 필요(검색 결과가 서로 엇갈려 단정하지 않는다). 실제 도입 전 caniuse· MDN에서 당일 기준을 확인할 것.

          💻 코드 (복붙용)

          /* ① 스태거 — JS로 --i 주입하던 코드를 통째로 삭제 */
.stagger li{
  opacity:0; transform:translateY(10px);
  transition:opacity .34s ease, transform .34s ease;
}
.stagger.play li{ opacity:1; transform:none; }

@supports (transition-delay: calc(sibling-index() * 1ms)){
  .stagger li{ transition-delay: calc(sibling-index() * 55ms); }
}

/* ② 개수 대비 비율 — 항목이 늘면 자동 재계산 */
.ramp li{
  background: color-mix(in oklab, var(--brand)
              calc(sibling-index() / sibling-count() * 100%), var(--surface-2));
}

/* ③ 동작 줄이기 존중 — 지연은 즉시 0 */
@media (prefers-reduced-motion: reduce){
  .stagger li{ transition-duration:.001s; transition-delay:0s !important; transform:none; }
}

          📈 왜 지금 뜨나 / 어디에 쓰나

          • 지금까지의 방법이 전부 나빴다. :nth-child(n) 하드코딩은 개수 제한이 있고, JS 인덱스 주입은 서버 렌더 결과와 어긋나 깜빡임을 만든다.
          • "몇 번째"가 레이아웃 값이 된다. 지연뿐 아니라 z-index(카드 겹침), rotate(부채꼴 펼침), 그리드 span까지 같은 방식으로 파생된다.
          • 리스트가 동적일수록 이득이 크다. 필터링으로 항목이 3개 ↔ 30개를 오가는 목록에서, JS 재계산이 통째로 사라진다.
          • 주의: 애니메이션에 쓰는 순간 접근성 체크가 따라온다 — 항목이 많으면 마지막 항목 등장까지 1초를 넘기지 말 것(체감상 "느린 페이지"가 된다).

          🧠 paysable 적용 포인트

          • 거래 목록·정산 내역이 필터 변경으로 갈아 끼워질 때, 스태거를 CSS만으로 붙여 "바뀌었다"는 신호를 준다(JS 코드 증가 0).
          • 결제 단계 스테퍼의 진행 색 농도를 sibling-count()로 잡으면, 단계 수가 다른 결제수단(카드 3단계 / 가상계좌 5단계)에 같은 CSS를 쓸 수 있다.
          • 단, 미지원 브라우저가 기능적으로 손해 보지 않는 용도(순수 장식)에만 쓴다. 값 계산·정렬 로직에는 아직 쓰지 않는다.
