🧭 명령 팔레트 — 메뉴를 찾는 대신 이름을 쳐서 간다 내비게이션·탭

화면이 30개를 넘어가면 사이드바는 더 이상 "찾는" 도구가 아니다. 요즘 관리자 도구는 ⌘K / Ctrl+K로 여는 검색형 내비게이션을 얹어, 이동·명령·데이터 검색을 한 입력창에서 처리한다. 핵심은 UI가 아니라 접근성 계약이다 — 포커스는 입력창에 그대로 두고, 화살표로 고르는 항목은 aria-activedescendant(가상 포커스: DOM 포커스를 옮기지 않고 "지금 고른 항목"만 알려주는 속성)로 알린다.

변형 A — 모달 팔레트 (dialog + combobox)

열기 → 타이핑 → ↑↓ → Enter

> 명령만 · # 거래만 · @ 화면만 — 접두사를 치면 칩으로 바뀌고, 빈 입력에서 Backspace로 풀립니다.
    ↑↓ 이동 Enter 실행 Esc 닫기
    아직 실행한 명령이 없습니다.

    <dialog>.showModal()이 포커스 가두기·Esc 닫기·배경 비활성화를 브라우저 몫으로 넘긴다. 우리가 직접 짜는 건 검색·정렬·키보드 하이라이트뿐이다.

    변형 B — 인라인 콤보박스 (모달 없이 화면 안에서)

    같은 ARIA 계약, 다른 껍데기

      선택: (없음)

      팔레트는 전역 이동·명령에, 인라인 콤보박스는 이 폼의 한 값 고르기에 쓴다. 둘의 ARIA 역할 구성은 똑같다 — 껍데기만 dialog냐 필드냐의 차이다.

      내비게이션 방식 비교
      방식언제 쓰나주의점
      정적 사이드바화면 10개 이하, 신규 사용자 탐색깊어지면 접기 지옥. 09-10 자 사이드바 편 참고
      모달 팔레트 오늘숙련 사용자가 많은 내부 도구·관리자단독으로 쓰면 신규 사용자는 존재를 모른다 → 사이드바와 병행
      인라인 콤보박스 오늘폼 안에서 값 하나 고르기선택값이 필드에 남아야 함. 모달처럼 사라지면 안 됨

      💻 코드 — combobox 계약의 뼈대

      <!-- 포커스는 input에 머문다. 화살표가 옮기는 건 "가상 포커스"뿐 -->
<input role="combobox" aria-expanded="true" aria-controls="list"
       aria-autocomplete="list" aria-activedescendant="opt-3">
<ul id="list" role="listbox">
  <li role="group" aria-label="이동">
    <div role="option" id="opt-3" aria-selected="true">거래 내역</div>
  </li>
</ul>
      // 화살표: DOM 포커스를 옮기지 말고 activedescendant만 갱신
function move(delta){
  idx = (idx + delta + opts.length) % opts.length;
  opts.forEach((o,i)=> o.setAttribute('aria-selected', i===idx));
  input.setAttribute('aria-activedescendant', opts[idx].id);
  opts[idx].scrollIntoView({ block:'nearest' });   // 스크롤은 우리가 책임진다
}

      ♿ 접근성·상태 설계

      • 포커스는 input에서 나가지 않는다. 화살표로 .focus()를 옮기면 타이핑이 끊긴다. aria-activedescendant만 바꾼다.
      • 결과 0건은 조용히 두지 말 것. aria-expanded="false"로 되돌리고, 안내 문구는 role="status" 영역에서 읽히게 한다.
      • 단축키 충돌: Ctrl/⌘+K는 일부 브라우저의 주소창 검색과 겹친다. preventDefault()를 하되, 버튼 진입로를 반드시 함께 제공한다(키보드를 못 쓰는 사용자·모바일).
      • 스크롤은 수동: 가상 포커스는 브라우저가 스크롤해 주지 않으므로 scrollIntoView({block:'nearest'})가 필요하다.
      • Esc 2단: 스코프(칩)가 있으면 먼저 스코프를 풀고, 그다음 눌렀을 때 닫히는 구현도 흔하다. 이 데모는 Esc = 즉시 닫기(dialog 기본)로 두고 Backspace로 스코프를 푼다.
      paysable 적용 포인트 — 운영/CS가 하루에 수십 번 하는 "거래번호로 점프", "이 건 부분취소", "테스트 모드 전환"을 팔레트 한 곳에 모으면 클릭 3~4회가 타이핑 몇 글자로 준다. 다만 결제 취소 같은 파괴적 명령은 팔레트에서 바로 실행하지 말고 확인 단계로 보내야 한다(09-08 자 파괴적 액션 확인 편).

      🃏 다중 선택과 일괄 작업 바 — 248건 중 무엇을 고르고 있는지 말해주기 카드·리스트

      리스트에 체크박스를 다는 건 쉽다. 어려운 건 선택 상태를 정직하게 표현하는 것이다 — 헤더 체크박스의 부분 선택(indeterminate), Shift 범위 선택, "이 페이지만 vs 조건에 맞는 전체", 그리고 선택이 생겼을 때만 나타나는 일괄 작업 바.

      변형 A — 테이블 다중 선택 + 하단 액션 바

      행을 클릭해 보고, Shift+클릭으로 범위도 잡아보세요

      정산 예정 거래 목록 (다중 선택 가능)
      거래번호가맹점금액상태
      0건 선택됨

      선택된 항목이 없습니다.

      액션 바는 선택이 0건이면 사라진다. 항상 떠 있으면서 회색으로 죽어 있는 버튼 줄보다, "선택했더니 할 수 있는 일이 나타난다"가 인과가 분명하다.

      변형 B — 카드 그리드 선택 (:has로 선택 상태 그리기)

      같은 선택 모델, 밀도가 낮은 카드 배치

      카드 전체를 <label>로 감싸면 어디를 눌러도 선택되고 체크박스는 진짜 폼 컨트롤로 남는다. 선택 테두리는 label:has(input:checked) — 상태 클래스를 JS로 붙일 필요가 없다.

      💻 코드 — 부분 선택과 Shift 범위

      // ① 헤더 체크박스의 3번째 상태: indeterminate (속성이 아니라 프로퍼티)
function syncHeader(){
  const n = rows.filter(r => r.checked).length;
  head.checked = n === rows.length && n > 0;
  head.indeterminate = n > 0 && n < rows.length;  // HTML 속성으로는 못 쓴다
}

// ② Shift 범위 선택 — 마지막으로 "직접 건드린" 행을 기억해 둔다
let lastIdx = null;
row.addEventListener('click', e => {
  const i = rows.indexOf(e.currentTarget);
  if (e.shiftKey && lastIdx !== null) {
    const [a,b] = [Math.min(lastIdx,i), Math.max(lastIdx,i)];
    for (let k=a;k<=b;k++) rows[k].checked = e.currentTarget.checked;
  }
  lastIdx = i;   // shift 클릭이어도 기준점은 갱신한다
  syncHeader();
});

      ♿ 접근성·상태 설계

      • 선택 개수를 말로 알린다. 색이 바뀐 행은 스크린 리더에 전달되지 않는다. role="status" 영역에 "12건 선택됨"을 넣는다(이 데모에 들어 있다).
      • indeterminate는 DOM 프로퍼티다. <input indeterminate>라고 써도 먹지 않고, JS로 el.indeterminate = true 해야 한다.
      • 페이지 선택 ≠ 전체 선택. 이 페이지 8건을 다 고른 뒤 "조건에 맞는 248건 전체 선택"을 따로 제안한다. 둘을 섞으면 의도치 않은 일괄 처리가 난다.
      • Shift 범위는 마우스 전용 편의다. 키보드만 쓰는 사용자에게는 헤더 전체 선택 + 개별 토글이 대체 경로가 되어야 한다.
      • 액션 바가 마지막 행을 가리지 않게 — position:sticky; bottom:0은 콘텐츠를 덮는다. 목록 하단에 액션 바 높이만큼 여백을 주거나(이 데모는 컨테이너 안에 고정) 스크롤 패딩을 준다.
      paysable 적용 포인트 — 정산 승인·증빙 일괄 다운로드처럼 "여러 건을 한 번에"가 잦은 화면의 표준 뼈대다. 실행 결과는 전부 성공/전부 실패로 끝나지 않으므로, 09-11 자 부분 성공 결과 리포트와 짝으로 붙여야 완성된다. 금액이 오가는 일괄 작업은 확인 단계에 선택 건수와 합계 금액을 반드시 다시 보여줄 것.

      🌀 CSS 앵커 포지셔닝 — 툴팁·팝오버를 JS 없이 기준 요소에 붙이기 트렌드·개념

      지금까지 드롭다운을 버튼 아래에 붙이려면 Floating UI 같은 라이브러리가 getBoundingClientRect()를 재고 스크롤·리사이즈마다 다시 계산해야 했다. 앵커 포지셔닝은 이걸 CSS 한 겹으로 옮긴다 — 기준 요소에 이름표(anchor-name)를 달고, 떠 있는 요소가 그 이름을 참조(position-anchor)하면 브라우저가 위치를 유지한다. 화면 밖으로 밀리면 position-try-fallbacks로 알아서 뒤집는다.

      지원 여부 확인 중…

      변형 A — 앵커에 붙는 팝오버 메뉴 (위치 바꿔보기)

      position-area 값을 바꾸면 메뉴가 버튼 주위를 돈다

      position-area:
      아직 선택하지 않았습니다.

      popover 속성이 열고 닫기·바깥 클릭 닫기·Esc·top layer를 담당하고, 앵커 포지셔닝이 어디에 뜰지만 담당한다. 역할이 깔끔하게 갈린다.

      변형 B — 툴팁: @supports로 구형 브라우저 폴백

      지원되면 앵커, 아니면 부모 기준 absolute — 둘 다 같은 자리에 뜬다

      이번 달 정산 예정액 ₩2,445,400 건당 2.9% + ₩100 (VAT 별도) · 정산일 기준으로 차감됩니다

      기본 CSS는 .tipwrap{position:relative} + .tip{position:absolute}로 두고, @supports (anchor-name: --x) 블록 안에서만 앵커 방식으로 덮어쓴다. 미지원 브라우저는 폴백을 그대로 쓰므로 기능 손실이 0이다.

      💻 코드 (복붙용)

      /* ① 기준 요소에 이름표를 단다 (dashed-ident: 반드시 -- 로 시작) */
.trigger { anchor-name: --pay-btn; }

/* ② 떠 있는 요소가 그 이름을 참조한다 */
.menu {
  position: fixed;              /* absolute/fixed 여야 한다 */
  inset: auto; margin: 6px;     /* popover UA 기본값(inset:0; margin:auto) 해제 */
  position-anchor: --pay-btn;
  position-area: block-end center;        /* 앵커의 아래·가운데 */
  position-try-fallbacks: flip-block, flip-inline;  /* 잘리면 위로/반대로 뒤집기 */
}

/* ③ 미지원 브라우저용 폴백을 "기본"으로 두고, 지원될 때만 덮어쓴다 */
.wrap { position: relative; }
.tip  { position: absolute; left: 50%; bottom: calc(100% + 8px); translate: -50% 0; }
@supports (anchor-name: --x) {
  .tip { position: fixed; position-anchor: --tip-btn;
         position-area: block-start center; left: auto; bottom: auto; translate: none; }
}

      📈 왜 지금 뜨나 / 어디에 쓰나

      • 브라우저 지원 — Chrome·Edge 125+, Firefox 132+, Safari 18.2+에서 지원된다고 보고된다(2026-09 검색 기준). 다만 @position-try·position-area 같은 세부 기능은 브라우저마다 도입 시점이 달라, 세부 지원 범위는 미검증·추정으로 본다. 실무에선 @supports 폴백을 반드시 깐다.
      • 번들이 준다 — 팝오버 위치 계산만을 위해 포지셔닝 라이브러리를 넣던 관행을 걷어낼 수 있다(얼마나 줄지는 프로젝트마다 다르므로 수치는 단정하지 않는다).
      • 스크롤 컨테이너 안에서 강하다 — 오버플로 있는 테이블·드로어 안의 드롭다운은 JS 계산이 가장 자주 깨지던 지점이다. CSS로 옮기면 스크롤 이벤트 리스너가 통째로 사라진다.
      • 같이 쓰면 좋은 것: popover 속성(top layer·Esc·light dismiss), 그리고 08-31 자 Invoker Commands. 열고 닫기는 HTML, 위치는 CSS, JS는 데이터만.
      paysable 적용 포인트 — 거래 테이블 행마다 붙는 액션 드롭다운, 금액 옆 수수료 툴팁, 필터 팝오버가 1차 후보다. 특히 가로 스크롤되는 테이블 안의 드롭다운은 지금 JS 위치 계산이 가장 자주 어긋나는 곳이라 교체 효과가 크다. 단, 결제 수단 선택처럼 실패하면 안 되는 흐름은 앵커 미지원 시에도 자리가 맞는 폴백을 먼저 확인하고 넣을 것.
